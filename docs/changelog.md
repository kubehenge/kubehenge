# Changelog

Every release's changes, newest first. Versions follow [Semantic Versioning](https://semver.org/); before 1.0.0 a minor version may change behaviour.

## [Unreleased]

- A cluster's volume owner VM is created under another VM ID when the one Proxmox VE offered is taken by a VM created at the same moment, instead of the cluster's setup failing until its next try.
- A kubeadm cluster's first control-plane node moves kube-vip from kubeadm's super-admin credentials to `admin.conf` while it is still bootstrapping, and finishes only once the new kube-vip holds the control-plane address. Until now the old kube-vip ran on for two minutes after `kubeadm init` and then left the address unanswered for about ten seconds, under whatever used the cluster by then.
- **Backups.** Backups with Velero to the S3 stores an administrator sets, on a schedule and kept for as long as the cluster chooses, each cluster under a prefix of its own and encrypted with keys of its own (SSE-C for its resources, Kopia for its volumes' data), `kube-system` left out; the cluster page lists the backups and restores, backs up at once and restores the whole cluster or chosen namespaces, restoring only for those who may download its admin kubeconfig.
- **Node OS refresh.** The management cluster builds the Ubuntu VM templates again every week with Ubuntu's updates (on by default, Sunday at 01:00 UTC, set on the Administration page or with the module's `template_refresh`), with an API token of its own that may build and delete templates in the template pool and nothing else. Each build is a template of its own; a cluster's nodes move to a new one inside its maintenance window once it is a day old, one at a time, whether automatic Kubernetes upgrades are on or not, unless the cluster switches it off. The two newest builds of each template stay, with any a cluster still runs. The cluster page shows which build the nodes run and when they next move; the Administration page shows the last run with its log and has Build now; where the administrator allows it, those who may create clusters can have a missing template built from the create wizard. A new build keeps the CPU type of the template it replaces, and with `--proxmox-insecure` the builds reach the API without verifying its certificate too.

## [0.2.0] - 2026-10-22

- **The Gateway API** in every cluster, so that Gateways and HTTPRoutes work beside Ingresses: the standard channel's CRDs, with the admission policy upstream ships to refuse older or experimental ones over them, and Traefik's Gateway `traefik-gateway` in `kube-system`, listening for HTTP where Traefik does and taking HTTPRoutes from every namespace. RKE2's and k3s's CRDs stay theirs while they ship them; Kubehenge brings its own release where they do not, never an older one over a newer. Istio's waypoints are Gateways of the class `istio-waypoint`.
- **Leader leases through stalls.** The control planes' controller managers and schedulers, and the cloud controller managers, CSI controller and Cilium operator Kubehenge installs, keep their leader leases through a stall of up to 40 seconds rather than restart, which on k3s would take its etcd member down with them while a single control plane is replaced.
- **The health page reads a stopped container's log** from its newest run that has ended, which the kubelet always keeps, instead of now and then showing an error where the log of a crash-looping pod should be.
- **The CSI plugin's newest release, per cluster.** With `cluster_datastore_allocate` (**CSI plugin** in the setup), a cluster may choose the Proxmox VE CSI plugin's newest release in the wizard, under **Options** or with its `csi` variable; its token then gets `Datastore.Allocate` on the cluster's storage. Only on a storage the management cluster, the VM templates and other clusters do not use. Other clusters keep the release that needs no `Datastore.Allocate`.
- **HA rules for cluster creators.** An administrator can have Proxmox VE's HA node-affinity rules offered as placements to everyone who may create or change a cluster, without `Sys.Audit` on `/` of their own (the setup's HA rules for cluster creators, or the module's `offer_ha_rules`; off by default). Kubehenge's controller reads them with its own token, which holds that privilege already, and the interface hands out each rule's name and the nodes it allows, nothing more.
- **The Proxmox VE API's address.** The installer reaches the API only at a name or address of the Proxmox VE cluster's own nodes that its certificate is valid for, never another host the certificate also names: a name for several nodes first, then this node's names, its addresses, a name without a domain, and the other nodes' names and addresses. A wildcard counts for this node's own name. Where several are as good, it asks on the terminal; where none is left, it stops and says what the certificate names.
- **The Proxmox VE API's CA.** Without `--proxmox-ca`, a certificate the cluster's CA did not sign is checked against the CA in the node's trust store it rests on, which the appliance and the clusters are given alone; failing that, against the CA the API serves, once the administrator has said yes to its fingerprint on the terminal. `--proxmox-ca` takes a bundle such as a whole trust store, reduced to the CA the certificate rests on, and a CA that is not self-signed.
- **`--proxmox-insecure`**, for the installer and `--upgrade`: the appliance, OpenTofu's and Cluster API's Proxmox VE providers, Kubehenge's controller and the clusters' cloud controller manager and CSI plugin reach the API without verifying its certificate. The Administration page shows it; `--upgrade --proxmox-ca` turns verification back on.
- The installer's check of the API's certificate, and its check of whether it made the appliance's own certificate, trust only the CA file given, not the node's default trust store besides.

## [0.1.0] - 2026-10-22

The first release.

- **Appliance.** One script on a Proxmox VE 9 node installs a small unprivileged container running Kubehenge's web interface. Users sign in with their Proxmox VE accounts, any realm, and act with their own Proxmox VE permissions. The appliance upgrades itself from a button, or automatically within a major version, and installs only releases signed with the project's release key, unpacking each where none of its entries can write outside the release's own directory. Its certificate is signed by the Proxmox VE cluster's CA, or is one of your own; it can carry a DNS name and drop it again, is renewed from the Proxmox VE shell, and the interface warns before it runs out. A Proxmox VE API whose certificate comes from another CA works too, with that CA given to the installer.
- **Management cluster.** Set up from the interface (or with the OpenTofu module in `management-cluster/`): a Talos Linux cluster of one or three VMs, spread over the Proxmox VE nodes chosen, running Cluster API, the Proxmox VE provider, the kubeadm, RKE2 and k3s providers, IP address management and the Helm add-on provider. The Proxmox VE provider runs as Kubehenge's own reproducible, signed build of an upstream commit after its v0.9.1 release, which carries the fix kubeadm upgrades need, until a release of it does. A distribution's controllers run only while a cluster uses it. The controllers hold their leader leases through API stalls of up to 40 seconds, as when Proxmox VE clones a disk on the same storage, instead of restarting, and every controller has a memory request, so none is the first a node short of memory stops.
- **Workload clusters** from three ClusterClasses, kubeadm, RKE2 and k3s: create, scale, upgrade by one minor version at a time, replace failed nodes, delete. Each cluster gets the Proxmox VE cloud controller manager, the Proxmox CSI plugin, a control-plane virtual IP with kube-vip, a CNI (the distribution's own, or Cilium or Calico chosen at creation), and Traefik as the ingress controller on every node (RKE2's and k3s's own; Kubehenge installs it on kubeadm). Services of type `LoadBalancer` get addresses of their own from a range on the nodes' network, with MetalLB (recommended) or kube-vip, chosen per cluster and refused where they clash with the nodes', the API address or another cluster's. Pod and service ranges, OpenID Connect sign-in and automatic upgrades within windows are set per cluster. While a cluster has workers, its control-plane nodes are tainted in every distribution and run only what has to run there; a cluster without workers runs its workloads on them. Control planes are sized by the distributions' server sizing guides, from 2 cores and 4096 MiB, with a worker's least on top when there are no workers, and a cluster whose control planes are too small for its workers is refused. The nodes that run the add-ons, the workers or else the control planes, need room for the add-ons chosen, by each add-on's measured memory; the interface raises the machines to it.
- **Health page.** Each cluster's page says whether it is healthy, changing, degraded or unreachable, and what needs attention first: nodes not ready or under pressure, pods that crash-loop, cannot pull their image or cannot be scheduled, volume claims still waiting, add-ons not deployed, failing readiness checks, worker pools short of machines and health checks holding back, with each VM's CPU over the last hour, the last hour's warnings and the cluster's conditions. It reads inside the cluster with read-only identities of its own, whose short-lived tokens the controller renews; pods' logs need `Sys.Modify` on the cluster's pool and come from an identity that reads logs only.
- **Placement.** A cluster's VMs spread over every online Proxmox VE node, or over the nodes chosen by hand or from one of Proxmox VE's HA node-affinity rules, and the choice can change later. A node that goes down is left out within about 15 seconds, so the VMs replacing those it ran go elsewhere. The cluster page shows where each VM runs and warns when control-plane VMs share a node. Where the administrator switches on Proxmox VE HA, it keeps every cluster's control-plane VMs on separate nodes and restarts them elsewhere after a node fails, for clusters on shared storage that do not opt out.
- **Isolation between clusters.** Each cluster has its own Proxmox VE pool, user and API token with rights on its own VMs only, and a VM that owns its persistent volumes, so a compromised cluster cannot reach another's VMs or volumes. Only the cloud controller manager and the CSI plugin's controller hold the token, on control-plane nodes only.
- **Add-ons.** Headlamp, per cluster or shared in the appliance behind its sign-in; Rancher, installed into a Kubehenge cluster, with the other clusters registered in it automatically; monitoring with kube-prometheus-stack, scraping every node and control-plane component over verified, authenticated TLS. kubeadm clusters' kubelets serve certificates from the cluster CA, which Kubehenge's controller approves and the API server verifies. Logs beside monitoring: Loki on a volume of its own, kept 7 days in 10 GiB unless set otherwise, behind a kube-rbac-proxy that lets nobody in without credentials and RBAC's leave, which Grafana Alloy has to push and monitoring's Grafana to read; Alloy collects on every node (container logs, short-lived pods' too, the journal and the API server's audit log) or, without access to the host, through the Kubernetes API. Pod security, a Pod Security Standard level enforced by Pod Security Admission, by Kyverno, or both, with the namespaces of the components that need the host exempt. CIS hardening, chosen at creation, beyond the baseline of the CIS Kubernetes Benchmark every cluster gets, checked with kube-bench in the end-to-end tests. Istio in ambient mode: mutual TLS between the pods of the namespaces enrolled, without sidecars; switching it off takes them out of the mesh first. Cilium Cluster Mesh, on kubeadm, RKE2 and k3s: clusters of one namespace that run Cilium and list each other reach each other's pods and global services; every new Cilium cluster gets a pod range of its own, and peers come and go without restarting anything.
- **Security baseline.** Every cluster audits its API server, encrypts Secrets in etcd, refuses requests without credentials beyond its health checks (and, on kubeadm, what `kubeadm join` reads), limits the rate of events, keeps its controller manager and scheduler on loopback, offers only strong TLS ciphers, and runs its kubelets on the kernel settings they expect.
- **Proxmox VE integration.** An optional entry in the Proxmox VE interface leading to the appliance (`appliance/pve-entry/`), added if the administrator says yes when installing.
- **Pinned by digest.** Every image, chart, provider file and tool Kubehenge deploys or builds with is named by its digest beside its version. Where the bytes are not stable or carry no digest, a signature is required instead: the Talos Image Factory's images and everything the management cluster pulls from registry.k8s.io, the control-plane images of kubeadm templates, and Ubuntu's cloud images and archive. RKE2 and k3s, which sign neither releases nor images, install from files checked against the checksums recorded when a cluster first uses the release.
