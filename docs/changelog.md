# Changelog

Every release's changes, newest first. Versions follow [Semantic Versioning](https://semver.org/); before 1.0.0 a minor version may change behaviour.

## [Unreleased]

- When the installer removes a container whose interface failed to start or to reach Proxmox VE's API, it prints the interface's log first, which went with the container before. Its check of the new appliance verifies the appliance's certificate instead of skipping it, and `install.sh --help` lists every option.
- `kubehenge template create` and `template refresh` refuse an empty `--node` before calling Proxmox VE.
- The documentation says HA group labels are on by default, as they are, and moves the setup's opt-in settings to a page of their own ([install-settings.md](install-settings.md)). Troubleshooting covers failed installs, template builds, a changed Proxmox VE CA, clusters refused when applied with kubectl, and each warning event the controller writes.
- A Cluster applied with kubectl or through GitOps is held to the interface's rules by the API server: a name of at most 40 characters, a version in the distribution's form, upgrades of one minor version at most and never back, 1, 3, 5 or 7 control-plane nodes, at most 100 workers in each pool, and node addresses and a control-plane endpoint on the gateway's network with the endpoint outside the node addresses ([clusters.md](clusters.md)). Fixed pools need node addresses for every machine plus one for a rollout, as autoscaled ones already did, since a rollout otherwise waits for ever.
- Two clusters on the same bridge and VLAN can no longer be given the same node addresses or control-plane endpoint, from the interface or kubectl alike.
- The management cluster's VMs get VM IDs picked at random between 10000 and 99999. Proxmox VE offers whatever is created at the same moment the same next free ID, and when another VM, such as a template being built, took it first, the Terraform/OpenTofu provider for Proxmox VE took that VM for the node it was creating: it changed and started it and kept it in its state, to be destroyed with the node.
- A cluster's machine whose clone fails is cloned again under a new VM ID. capmox kept the ID of the failed clone, which a VM created at the same moment may have taken; the machine then waited on that VM for ever and, once deleted, deleted it with itself.
- Deleting a cluster's machine destroys its VM only once the VM under the machine's VM ID is confirmed as the machine's, by its name and SMBIOS UUID; a free ID, or one held by another VM or a container, counts as the VM gone. Proxmox VE hands a freed ID to the next clone, and capmox's next pass over the deletion could destroy that clone, possibly a machine of another cluster.

## [0.3.1] - 2026-10-28

- capmox, which creates the clusters' VMs, is built from a later commit of its main branch. A machine whose VM needs no configuration change is started instead of being reported ready while its VM stays off, and a transient error while attaching the bootstrap ISO is retried instead of failing the machine for good.
- The installer names the address of a download that still fails after its retries, where curl's own message gives only the HTTP status.

## [0.3.0] - 2026-10-27

- The interface has a look and a frame of its own: the fleet down the left of every page, grouped into those that need you, those with work running and the healthy, each with why, counting what each cluster's health page finds; the work under way down the right, snapshots, backups, restores, template builds and the appliance's upgrades included, a failed run with its first error; a cluster's views as tabs under its name, its summary opening on its machines laid out by Proxmox VE node; a cluster's changes staged first, checked by the API server, and applied together after a plan that says what each replaces ([clusters.md](clusters.md#staged-changes)), then followed as a run whose page counts the machines replaced; a page for every run, its first error pinned above its steps; Administration in four short pages, the management cluster, the appliance, templates and certificates; **Go to or run…** (`Ctrl K`) to find any cluster, view or action by a few letters; and single keys for the rest ([clusters.md](clusters.md#finding-your-way)). It follows the system's dark or light mode, with Atkinson Hyperlegible Next for text and JetBrains Mono for names, versions and addresses.
- **Talos clusters.** A ClusterClass for Talos Linux (`kubehenge-talos`), with the same variables, add-ons and checks as the others but `nodeOS`, since Talos is its own OS, and one more, `talosVersion`, the Talos release the nodes run. Its control planes hold their address with Talos's own virtual IP, and its CNI is Talos's flannel unless the cluster chooses Cilium or Calico. Templates come from the Talos Image Factory, one per release, built on the Administration page, from the create wizard where creators may ask for one, or with `kubehenge template create talos --talos-version`. Changing `talosVersion` upgrades the nodes in place through the Talos API, one at a time, control planes first and each drained first, a minor version at a time; one that fails or rolls back stops the rest until **Try again** on the cluster's page. With node image updates on, the nodes move to new Talos patch releases inside the maintenance window. The cluster page shows the release, the upgrade under way and the last one, and downloads the talosconfig for those who may download the kubeconfig; etcd snapshots are taken and restored through the Talos API, the restore wiping etcd on every control plane, recovering it on the first and letting the others join again. Talos's service and kernel logs reach Loki through the node collector, under `job="talos"`. Each machine's configuration is generated in the schema of the Talos release it boots first. Of each Talos minor version the template refresh keeps the two newest releases' templates and any a cluster still boots or is upgraded to. Not yet on Talos: the controller manager's and scheduler's metrics, which Talos serves with certificates nothing can verify; Kubehenge scrapes them on the first Talos release that gives them certificates of the cluster CA. The Talos bootstrap and control-plane providers come from Kubehenge's own forks of them, [cluster-api-bootstrap-provider-talos](https://github.com/kubehenge/cluster-api-bootstrap-provider-talos) and [cluster-api-control-plane-provider-talos](https://github.com/kubehenge/cluster-api-control-plane-provider-talos), on Cluster API's v1beta2 contract and with the control-plane template a ClusterClass needs; they are maintained primarily for Kubehenge and open to anyone. Their files and images are pinned by digest, and the management cluster's nodes pull the images only with the signature of the fork's release workflow; like every distribution's, their controllers run only while a cluster uses Talos.
- **Backups.** Backups with Velero to the S3 stores an administrator sets, on a schedule and kept for as long as the cluster chooses, each cluster under a prefix of its own and encrypted with keys of its own (SSE-C for its resources, Kopia for its volumes' data), `kube-system` left out; the cluster page lists the backups and restores, backs up at once and restores the whole cluster or chosen namespaces, restoring only for those who may download its admin kubeconfig.
- **Node OS refresh.** The management cluster builds the node OS VM templates again every week with their node OS's updates (on by default, Sunday at 01:00 UTC, set on the Administration page or with the module's `template_refresh`), with an API token of its own that may build and delete templates in the template pool and nothing else. Each build is a template of its own; a cluster's nodes move to a new one inside its maintenance window once it is a day old, one at a time, whether automatic Kubernetes upgrades are on or not, unless the cluster switches it off. The two newest builds of each template stay, with any a cluster still runs. The cluster page shows which build the nodes run and when they next move; the Administration page shows the last run with its log and has Build now; where the administrator allows it, those who may create clusters can have a missing template built from the create wizard. A new build keeps the CPU type of the template it replaces, and with `--proxmox-insecure` the builds reach the API without verifying its certificate too.
- **HA group labels, per cluster.** The cloud controller manager labels each cluster's nodes with their Proxmox VE HA groups or HA node-affinity rules, and no longer logs a permission error for them every few minutes: the cluster's token gets `Sys.Audit` on `/`, unpropagated, through a group the controller adds its user to, which lets it read the Proxmox VE cluster's own configuration and change nothing. A cluster switches the labels off in the wizard, under **Options** or with its `ccm` variable; an administrator switches them off for every cluster with **HA group labels** in the setup or the module's `cluster_sys_audit`.
- **More namespaces for clusters.** An administrator can name namespaces beside `clusters` that the interface creates and manages clusters in, such as one per team: **Namespaces for clusters** in the setup, `extra_cluster_namespaces` in the module, `interface.extraNamespaces` in the chart. Off by default. The wizard then asks for the namespace and the cluster list shows it ([clusters.md](clusters.md#more-namespaces-for-clusters)).
- **Read-only Headlamp for everyone.** A cluster's own Headlamp add-on can show the cluster to everyone who reaches it without signing in (`headlamp.access: view`, in the wizard and the Options view; off by default): its service account is bound to Kubernetes' `view` ClusterRole and Headlamp uses it for every request, so it shows workloads, ConfigMaps, events and logs, no Secrets, and changes nothing.
- **Volume snapshots, per cluster.** With `cluster_volume_snapshots` (**Volume snapshots** in the setup, with `root@pam`'s password), a cluster on storage local to each node (ZFS, LVM, LVM-thin, directory or btrfs) may take VolumeSnapshots, restore them and clone volumes, in the wizard, under **Options** or with its `csi` variable's `volumeSnapshots`. Proxmox VE copies volumes only for `root@pam`, so that cluster's CSI plugin signs in as `root@pam`, and whoever takes over the cluster holds the Proxmox VE cluster. It gets the VolumeSnapshotClass `proxmox` and, on kubeadm and k3s, the snapshot controller; RKE2 uses its own. Switching it on takes `Permissions.Modify` on `/`. Off by default ([clusters.md](clusters.md#volume-snapshots)).
- **Certificates.** Certificates with cert-manager: from Let's Encrypt or any ACME server, proved by DNS-01 through Cloudflare, Route 53, DigitalOcean, Azure DNS, Google Cloud DNS, RFC 2136, ACME-DNS or Akamai, or by HTTP-01 through Traefik's Gateway, or from a CA of the cluster's own, constrained to its domain and downloadable from the interface. With DNS-01 or the CA, a wildcard certificate for the cluster's domain is Traefik's default and its Gateway's HTTPS listener's; the add-ons' Ingresses ask for their own where it does not cover them. The DNS provider's credential is typed into the interface, per cluster or, for clusters that opt in with `Sys.Modify`, once for every cluster; or it stays in a Secret of the cluster's own.
- **GitOps.** Argo CD or Flux per cluster, off by default, keeping it in step with a directory of a Git repository and leaving what it deployed running when switched off or to the other engine. A private repository is read with a deploy key Kubehenge makes and the interface shows, with a stored token, or with a Secret of the owner's own; over SSH the server's host keys are read once and trusted from then on. Argo CD signs in through the cluster's first identity provider with PKCE, its local admin disabled, and gives rights only to the groups named its admins; Flux is installed at a pinned version by the Flux Operator, whose web interface is an opt-in. Choosing the repository needs `Sys.Modify` on the pool, as the admin kubeconfig does.
- **Cluster autoscaler.** A worker pool can be autoscaled, at creation or later from the Scale dialog, between a fewest of 0 to 100 and a most of up to 100 workers: the cluster autoscaler of the cluster's Kubernetes minor adds workers while pods wait for room and removes those left unneeded, scaling up from none by the pool's machine size, with a 10% margin, and node labels. It runs in the management cluster with a token into its cluster, 64 MiB requested each, or, chosen under Options with `VM.Audit` on the workload pool, on the cluster's own control planes; an admission policy holds each autoscaler to its own cluster's pools and machines. Control planes stay tainted while a pool may grow, add-ons need a pool that keeps a worker, the node addresses must hold every pool at its most, the Scale dialog warns when the Proxmox VE nodes lack the memory for the most, and a worker that finds no room shows `AutoscalerNoRoom`. Switching it off fixes the pool at the workers it runs and removes everything the autoscaler was given.
- **etcd snapshots.** Kubehenge's controller takes each cluster's etcd on a schedule, or at once from the cluster page, into the same S3 stores as backups, encrypted with age to a key of the cluster's own, checked against etcd's own checksum and kept for as many as the cluster chooses, with no etcd key or store credential in the cluster; the cluster page lists them, downloads them for those with the right and restores one, stopping every control plane, restoring etcd on one and replacing the others, through the Proxmox VE guest agent where an administrator switched that on and as steps to run by hand where not. On RKE2 and k3s a cluster may also opt into the distribution's own upload of the snapshots its servers take, off by default, to the same target with its certificate verified: that puts the target's access key into a Secret in the cluster's `kube-system`, keeps it out of the machines' bootstrap data, and stores those snapshots unencrypted for restoring by hand.
- **Headlamp sign-in.** An administrator can have the shared Headlamp open each cluster signed in as cluster-admin for those who hold `Sys.Modify` on its pool, the privilege its admin kubeconfig takes (the setup's Headlamp sign-in, or the module's `headlamp_sign_in`; off by default). The token is made for the session, lasts an hour at most and never longer than the session, and stays in the appliance; the interface logs each one with its user and the token's ID, which the cluster's audit log records. Switching it off removes the accounts behind it from every cluster, which ends every token made. Logging out of a cluster in Headlamp drops the session's token until the cluster is opened from the interface again.
- **Headlamp's log out works in the shared Headlamp.** The gate refused the requests with which Headlamp clears a cluster's token and ends an identity provider's sign-in; it now passes them on for the clusters the user sees.
- **Management cluster upgrades.** Every apply records the Kubehenge release that ran it, and once the appliance runs a newer one the Administration page says so, with **Upgrade the management cluster**, which lists the components whose versions change and applies the settings as they are with the state passphrase. Off by default, the management cluster can also follow the appliance's upgrades on its own, in their hour, at most once a day, a failed run waiting for the next day; switching it on has the appliance keep the state passphrase and the API token of a Proxmox VE user of its own with the Administrator role, as the dialog says, and switching it off, or removing the management cluster, deletes both.
- **Headlamp actions.** An administrator can have the shared Headlamp offer the Helm app catalog and the Prometheus charts it ships with (the setup's Headlamp actions, or the module's `headlamp_actions`; off by default). Everyone who sees a cluster lists, installs, upgrades, rolls back and uninstalls its Helm releases with their own credentials in it, or the sign-in's, and charts its metrics from a Prometheus running there. Charts come only from the Helm repositories set for the appliance, which only those who may set the appliance up add or remove, over HTTPS. Port forwards stay with Headlamp's desktop app.
- **Node OSes instead of Ubuntu.** The nodes of RKE2, k3s and kubeadm clusters run a node OS each cluster chooses with its `nodeOS` variable, in the wizard or under **Options**: AlmaLinux 10 by default, or Rocky Linux 10 (on `x86-64-v3` CPUs), both in image mode, a bootable container image made of the family's own signed packages with a read-only `/usr`; openSUSE Leap 16.1 Immutable follows once openSUSE releases it. Each holds only what a node needs (cloud-init, the QEMU guest agent, the SELinux policies, and for kubeadm containerd and the kubelet's tools) and enforces SELinux: containerd with its SELinux support, RKE2 and k3s with their own policies, and on kubeadm the control plane's static pods and kube-vip as `spc_t` while every other pod stays confined. The QEMU guest agent runs what Proxmox VE sends it unconfined, as a root shell would. Changing the node OS replaces the nodes one at a time once its template is built. Clusters are placed only on Proxmox VE nodes whose CPU runs their node OS, and refused one none of their nodes can. RKE2 and k3s now have a template each per node OS, for their policies; `kubehenge template` takes `--node-os`. Ubuntu templates are no longer made or selected: build the new templates before upgrading, and existing clusters move to them as the ClusterClasses change.
- An AlmaLinux or Rocky Linux template build leaves a mirror that serves its packages at under 100 kB/s for the next one in the mirror list. Until now it stayed on the mirror down to 1000 bytes/s, and a build could run past its 45 minutes on one serving 50 kB/s.
- An AlmaLinux or Rocky Linux template build tries each step that reads the family's repositories up to three times, half a minute apart. A mirror caught syncing can serve a broken file, such as a `repomd.xml` that is not XML, and dnf and rpm-ostree do not move to the next mirror for it, so a refresh failed.
- A k3s cluster with flannel runs kube-proxy in nftables mode. In iptables mode, k3s's network policy controller could overwrite kube-proxy's rules while a node started, and that node's pods then reached no Service, the API server among them, until a Service changed or an hour had passed.
- The nodes that run the add-ons, the workers or else the control planes, need room for the CPU the add-ons' pods request as well as for their memory: Kubehenge refuses a cluster whose cores fall short, beside what the distribution's, the CNI's and its own pods request there, and the interface raises the cores to it and shows the add-ons' requests on the Add-ons step. Without it, a pod the scheduler found no room for stayed pending with `Insufficient cpu`, however idle the node was. Each class carries the figures (`kubehenge.dev/addon-cpu`, `kubehenge.dev/node-cpu`, [clusters.md](clusters.md#machines)); every add-on but Rancher fits on one worker of the default 2 cores on every distribution.
- Kubehenge checks that a cluster's control planes have the memory its add-ons add to what each uses itself, mostly their resource types and objects in the API server, with workers as well as without, and the interface raises the control planes to it. With every add-on but Rancher an RKE2 control plane needs 4720 MiB, where 4096 MiB ran out of memory once Argo CD started. The figures are measured as each add-on is switched on ([clusters.md](clusters.md#machines)).
- A cluster's volume owner VM is created under another VM ID when the one Proxmox VE offered is taken by a VM created at the same moment, instead of the cluster's setup failing until its next try.
- A kubeadm cluster's first control-plane node moves kube-vip from kubeadm's super-admin credentials to `admin.conf` while it is still bootstrapping, and finishes only once the new kube-vip holds the control-plane address. Until now the old kube-vip ran on for two minutes after `kubeadm init` and then left the address unanswered for about ten seconds, under whatever used the cluster by then.
- An RKE2 or k3s server whose etcd member is removed, as its control plane is replaced, stays down until its VM is deleted. Until now it started again, joined etcd as a new member, and went with its VM as a voter etcd still counted, so a cluster with one server lost its quorum when the control plane was replaced under load. RKE2 and k3s control planes are replaced to get it.
- A control plane's API server runs with a Go memory limit of 40 % of the control plane's memory, half of it for k3s's server process. It sat at about twice what it holds, and a 4096 MiB kubeadm control plane ran out of memory when every add-on was switched off at once. Control planes are replaced to get it.

## [0.2.0] - 2026-10-22

- **The Gateway API** in every cluster, so that Gateways and HTTPRoutes work beside Ingresses: the standard channel's CRDs, with the admission policy upstream ships to refuse older or experimental ones over them, and Traefik's Gateway `traefik-gateway` in `kube-system`, listening for HTTP where Traefik does and taking HTTPRoutes from every namespace. RKE2's and k3s's CRDs stay theirs while they ship them; Kubehenge brings its own release where they do not, never an older one over a newer. Istio's waypoints are Gateways of the class `istio-waypoint`.
- **Leader leases through stalls.** The control planes' controller managers and schedulers, and the cloud controller managers, CSI controller and Cilium operator Kubehenge installs, keep their leader leases through a stall of up to 40 seconds rather than restart, which on k3s would take its etcd member down with them while a single control plane is replaced.
- **The health page reads a stopped container's log** from its newest run that has ended, which the kubelet always keeps, instead of now and then showing an error where the log of a crash-looping pod should be.
- **The CSI plugin's newest release, per cluster.** With `cluster_datastore_allocate` (**CSI plugin** in the setup), a cluster may choose the Proxmox VE CSI plugin's newest release in the wizard, under **Options** or with its `csi` variable; its token then gets `Datastore.Allocate` on the cluster's storage. Only on a storage the management cluster, the VM templates and other clusters do not use. Other clusters keep the release that needs no `Datastore.Allocate`.
- **HA rules for cluster creators.** An administrator can have Proxmox VE's HA node-affinity rules offered as placements to everyone who may create or change a cluster, without `Sys.Audit` on `/` of their own (the setup's HA rules for cluster creators, or the module's `offer_ha_rules`; off by default). Kubehenge's controller reads them with its own token, which holds that privilege already, and the interface hands out each rule's name and the nodes it allows, nothing more.
- **The Proxmox VE API's address.** The installer reaches the API only at a name or address of the Proxmox VE cluster's own nodes that its certificate is valid for, never another host the certificate also names: a name for several nodes first, then this node's names, its addresses, a name without a domain, and the other nodes' names and addresses. A wildcard counts for this node's own name. Where several are as good, it asks on the terminal; where none is left, it stops and says what the certificate names.
- **The Proxmox VE API's CA.** Without `--proxmox-ca`, a certificate the cluster's CA did not sign is checked against the CA in the node's trust store it rests on, which the appliance and the clusters are given alone; failing that, against the CA the API serves, once the administrator has said yes to its fingerprint on the terminal. `--proxmox-ca` takes a bundle such as a whole trust store, reduced to the CA the certificate rests on, and a CA that is not self-signed.
- **`--proxmox-insecure`**, for the installer and `--upgrade`: the appliance, OpenTofu's and Cluster API's Proxmox VE providers, Kubehenge's controller and the clusters' cloud controller manager and CSI plugin reach the API without verifying its certificate. The Administration page shows it; `--upgrade --proxmox-ca` turns verification back on.
- The installer's check of the API's certificate, and its check of whether it made the appliance's own certificate, trust only the CA file given, not the node's default trust store besides.

## [0.1.0] - 2026-10-22

The first release.

- **Appliance.** One script on a Proxmox VE 9 node installs a small unprivileged container running Kubehenge's web interface. Users sign in with their Proxmox VE accounts, any realm, and act with their own Proxmox VE permissions. The appliance upgrades itself from a button, or automatically within a major version, and installs only releases signed with the project's release key, unpacking each where none of its entries can write outside the release's own directory. Its certificate is signed by the Proxmox VE cluster's CA, or is one of your own; it can carry a DNS name and drop it again, is renewed from the Proxmox VE shell, and the interface warns before it runs out. A Proxmox VE API whose certificate comes from another CA works too, with that CA given to the installer.
- **Management cluster.** Set up from the interface (or with the OpenTofu module in `management-cluster/`): a Talos Linux cluster of one or three VMs, spread over the Proxmox VE nodes chosen, running Cluster API, the Proxmox VE provider, the kubeadm, RKE2 and k3s providers, IP address management and the Helm add-on provider. The Proxmox VE provider runs as Kubehenge's own reproducible, signed build of an upstream commit after its v0.9.1 release, which carries the fix kubeadm upgrades need, until a release of it does. A distribution's controllers run only while a cluster uses it. The controllers hold their leader leases through API stalls of up to 40 seconds, as when Proxmox VE clones a disk on the same storage, instead of restarting, and every controller has a memory request, so none is the first a node short of memory stops.
- **Workload clusters** from three ClusterClasses, kubeadm, RKE2 and k3s: create, scale, upgrade by one minor version at a time, replace failed nodes, delete. Each cluster gets the Proxmox VE cloud controller manager, the Proxmox CSI plugin, a control-plane virtual IP with kube-vip, a CNI (the distribution's own, or Cilium or Calico chosen at creation), and Traefik as the ingress controller on every node (RKE2's and k3s's own; Kubehenge installs it on kubeadm). Services of type `LoadBalancer` get addresses of their own from a range on the nodes' network, with MetalLB (recommended) or kube-vip, chosen per cluster and refused where they clash with the nodes', the API address or another cluster's. Pod and service ranges, OpenID Connect sign-in and automatic upgrades within windows are set per cluster. While a cluster has workers, its control-plane nodes are tainted in every distribution and run only what has to run there; a cluster without workers runs its workloads on them. Control planes are sized by the distributions' server sizing guides, from 2 cores and 4096 MiB, with a worker's least on top when there are no workers, and a cluster whose control planes are too small for its workers is refused. The nodes that run the add-ons, the workers or else the control planes, need room for the add-ons chosen, by each add-on's measured memory; the interface raises the machines to it.
- **Health page.** Each cluster's page says whether it is healthy, changing, degraded or unreachable, and what needs attention first: nodes not ready or under pressure, pods that crash-loop, cannot pull their image or cannot be scheduled, volume claims still waiting, add-ons not deployed, failing readiness checks, worker pools short of machines and health checks holding back, with each VM's CPU over the last hour, the last hour's warnings and the cluster's conditions. It reads inside the cluster with read-only identities of its own, whose short-lived tokens the controller renews; pods' logs need `Sys.Modify` on the cluster's pool and come from an identity that reads logs only.
- **Placement.** A cluster's VMs spread over every online Proxmox VE node, or over the nodes chosen by hand or from one of Proxmox VE's HA node-affinity rules, and the choice can change later. A node that goes down is left out within about 15 seconds, so the VMs replacing those it ran go elsewhere. The cluster page shows where each VM runs and warns when control-plane VMs share a node. Where the administrator switches on Proxmox VE HA, it keeps every cluster's control-plane VMs on separate nodes and restarts them elsewhere after a node fails, for clusters on shared storage that do not opt out.
- **Isolation between clusters.** Each cluster has its own Proxmox VE pool, user and API token with rights on its own VMs only, and a VM that owns its persistent volumes, so a compromised cluster cannot reach another's VMs or volumes. Only the cloud controller manager and the CSI plugin's controller hold the token, on control-plane nodes only.
- **Add-ons.** Headlamp, per cluster or shared in the appliance behind its sign-in; Rancher, installed into a Kubehenge cluster, with the other clusters registered in it automatically; monitoring with kube-prometheus-stack, scraping every node and control-plane component over verified, authenticated TLS. kubeadm clusters' kubelets serve certificates from the cluster CA, which Kubehenge's controller approves and the API server verifies. Logs beside monitoring: Loki on a volume of its own, kept 7 days in 10 GiB unless set otherwise, behind a kube-rbac-proxy that lets nobody in without credentials and RBAC's leave, which Grafana Alloy has to push and monitoring's Grafana to read; Alloy collects on every node (container logs, short-lived pods' too, the journal and the API server's audit log) or, without access to the host, through the Kubernetes API. Pod security, a Pod Security Standard level enforced by Pod Security Admission, by Kyverno, or both, with the namespaces of the components that need the host exempt. CIS hardening, chosen at creation, beyond the baseline of the CIS Kubernetes Benchmark every cluster gets, checked with kube-bench in the end-to-end tests. Istio in ambient mode: mutual TLS between the pods of the namespaces enrolled, without sidecars; switching it off takes them out of the mesh first. Cilium Cluster Mesh, on kubeadm, RKE2 and k3s: clusters of one namespace that run Cilium and list each other reach each other's pods and global services; every new Cilium cluster gets a pod range of its own, and peers come and go without restarting anything.
- **Security baseline.** Every cluster audits its API server, encrypts Secrets in etcd, refuses requests without credentials beyond its health checks (and, on kubeadm, what `kubeadm join` reads), limits the rate of events, keeps its controller manager and scheduler on loopback, offers only strong TLS ciphers, and runs its kubelets on the kernel settings they expect.
- **Proxmox VE integration.** An optional entry in the Proxmox VE interface leading to the appliance (`appliance/pve-entry/`), added if the administrator says yes when installing.
- **Pinned by digest.** Every image, chart, provider file and tool Kubehenge deploys or builds with is named by its digest beside its version. Where the bytes are not stable or carry no digest, a signature is required instead: the Talos Image Factory's images and everything the management cluster pulls from registry.k8s.io, the control-plane images of kubeadm templates, and Ubuntu's cloud images and archive. RKE2 and k3s, which sign neither releases nor images, install from files checked against the checksums recorded when a cluster first uses the release.
