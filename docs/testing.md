# Testing

Kubehenge is tested in four tiers, and only the last needs Proxmox VE.

| Tier | What it checks | Needs Proxmox VE |
| --- | --- | --- |
| Lint and static | formatting, lint and types of Go, the known vulnerabilities it reaches, the frontend, shell, Terraform/OpenTofu, YAML, Markdown, the workflows and the e2e image's Dockerfile, each at its strictest settings; the charts' values against their schemas | no |
| Unit | the interface's backend and frontend, and the template rendering; the fuzz tests' seeds (`go test -fuzz` runs one for longer; CI fuzzes every one for minutes on each pull request and for half an hour each week, `.github/workflows/fuzz.yml`) | no |
| Integration | the Helm charts and Kubehenge's controllers against a real Kubernetes API server carrying the CRDs of the Cluster API releases the management cluster installs, and of the Cluster API operator: every object against its schema, server-side apply, finalizers, status and scale | no |
| End to end | real clusters of VMs on Proxmox VE: create, scale workers up and down by hand and by the cluster autoscaler, upgrade Kubernetes by one minor version with nodes replaced one at a time, replace a failed node, delete; for each distribution and add-on | yes |

## Running them

`make test` runs `make lint` and `make unit`, and `make integration` runs on its own; their steps run side by side, one per CPU; each step can also run on its own, such as `make unit-go` or `make lint-web` (the targets are in the `Makefile`). The frontend's packages are installed again only when `web/package-lock.json` changes, and the frontend is built again only when one of its sources does. Every Go step first downloads the Gateway API's install file the controller carries, with curl, once per release (`make gateway-api`), and refuses it unless it matches the SHA-256 in the `Makefile`.

## End to end without a Proxmox VE host

CI runs the end-to-end tier with Proxmox VE in a container (`.github/workflows/e2e.yml`), one test per machine. A machine whose KVM lacks pause-loop exiting hands its test to a fresh one, up to three times: there guests that outnumber its CPUs starve each other whatever their sizes, so the check that nothing restarts with every add-on on would only measure the machine. A test still on such a machine at the fourth try runs there with restarts reported, not failed (`KUBEHENGE_E2E_RESTARTS=report`). The merge queue runs the tests all the changes of a merge group need together (`test/e2e/ci/scope.sh`: none for documentation alone, all of them for a change it cannot place), on the tree that would land on main, so no change reaches main without the tests it needs; a pull request runs the other tiers and leaves this one to the queue; and the nightly run runs every test and adds the management cluster's upgrade and Rancher, builds Proxmox VE's image afresh and keeps it, with Go's build cache, for the day's runs. Any Linux machine with Docker, `/dev/kvm` and about 14 GB of free memory can do the same:

```sh
scripts/tools.sh ~/.local/kubehenge-tools && export PATH=~/.local/kubehenge-tools:$PATH
test/e2e/ci/up.sh /tmp/e2e          # Proxmox VE in a container, a registry beside it
test/e2e/ci/run.sh /tmp/e2e rke2    # or management-cluster, management-cluster-upgrade, appliance, kubeadm, k3s, rancher, cluster-mesh, node-image-refresh, autoscaler
```

Each try records what the machine and its VMs take while the test runs, every 15 seconds: the machine's memory, swap, disk and CPUs, and per VM the CPU time, resident memory and swap of its QEMU process (`test/e2e/ci/guests.sh record`). The log's "The guests' load" step sums it up per minute and gives each VM's busiest minute and most memory, which is where a step that outgrows the machine shows: a VM swapped out, or the CPUs of all of them above the machine's. The machine keeps its page cache rather than the guests' memory under pressure (`vm.swappiness=10`) and starts reclaiming earlier (`vm.watermark_scale_factor=200`), so that cloning a template evicts cached disk blocks instead of a running control plane. When a test fails, the try's artifact holds, beside the clusters' objects and pods' logs (and the earlier run of every container that restarted), what each running VM held through its guest agent (`guests.sh collect`): its state and pressure, the distribution's services' journal and every line about etcd in it, the logs of the static pods and of restarted containers as the kubelet keeps them, the kernel's log, and etcd's members, status, health and metrics as the node sees them. These still read when a cluster's API no longer answers; tokens and passwords are redacted from them.

`up.sh` builds `test/e2e/pve`, a one-node Proxmox VE on Debian 13 that runs on the machine's own kernel and starts VMs on its KVM, so the clusters' VMs are nested one level deeper than the machine itself. Like every node it runs an SSH server and reaches itself over SSH as root, which `up.sh` checks: Proxmox VE copies a volume, such as a CSI volume snapshot, through SSH even within one node. It gives the VMs the bridge 172.20.99.0/24, with a name server on it that asks this machine's own (so the VMs need no public one), and the containers 172.21.99.0/24, routes this machine to the bridge (with `sudo`), and writes the settings `run.sh` reads. `run.sh` builds the controller from the working tree, pushes it to the registry, applies the management cluster (`test/e2e/ci/main.tf`) with the container's CA trusted by its own processes only (`SSL_CERT_FILE`; the machine's trust store is left as it is), creates the templates the test needs meanwhile and runs it; `management-cluster` runs the templates and volumes tests while the management cluster is up, before it destroys it; for `appliance` it builds two releases instead and runs the test in the container, whose appliance sets the management cluster up itself. Remove everything with `docker rm -f kubehenge-e2e-pve kubehenge-e2e-registry && docker network rm kubehenge-e2e` and `sudo ip route del 172.20.99.0/24`.

**Supported means the end-to-end suite passed.** A ClusterClass or add-on is listed as supported only once the end-to-end tier has run it in CI against a Proxmox VE host of the current release.
