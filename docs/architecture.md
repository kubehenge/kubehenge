# Architecture

Kubehenge assembles maintained upstream pieces into one tested whole for Proxmox VE. It writes as little of its own as it can: the cluster templates, the add-on catalogue, the image pipeline, the first-run bootstrap and the interface.

## Why Cluster API

Cluster API is the Kubernetes project's own way to describe clusters as Kubernetes objects and have controllers create and keep them in that state. VMware's vSphere Kubernetes Service and OpenStack's Magnum both run on it. It gives Kubehenge, for free:

- **Several distributions over one infrastructure layer.** The distribution is a swappable bootstrap and control-plane provider; Proxmox VE stays the same underneath.
- **Day two, not only day one.** Rolling upgrades with nodes replaced one at a time, scaling by changing a number, health checks that replace dead nodes, clean deletion.
- **GitOps.** Clusters are YAML, so they work from Git with any GitOps tool.

A Terraform/OpenTofu-only design would create clusters once and leave upgrades and node replacement to be rebuilt for every distribution.

## Components

```text
Kubehenge interface (the appliance, an LXC container on Proxmox VE)
        │ acts with a ServiceAccount of its own

management cluster (small, Talos, on Proxmox VE VMs; runs Kubehenge and nothing else)

 ├─ capmox                       infrastructure: clones Proxmox VE VM templates, sets CPU, memory

 ├─ bootstrap + control plane    kubeadm (Cluster API core) | RKE2 (Rancher) | k3s (k3s project) |
 │                               Talos (Sidero Labs)
 ├─ IP address management        in-cluster IP pools for node addresses
 ├─ Add-on Provider for Helm     installs each cluster's add-ons as Helm charts
 ├─ cert-manager                 certificates for the providers' webhooks
 ├─ Kubehenge ClusterClasses     one tested template per distribution
 ├─ Kubehenge controller         each cluster's Proxmox VE objects, add-ons, Rancher registration,
 │                               automatic upgrades, autoscalers
 └─ cluster autoscalers          one per cluster with an autoscaled pool, unless it runs in the
                                 cluster
        │
        ▼ creates and manages
workload clusters on Proxmox VE VMs
 ├─ always: Proxmox CSI plugin, Proxmox cloud controller manager, control-plane virtual IP, CNI,
 │          Traefik, the Gateway API
 └─ chosen: Rancher, Headlamp, monitoring, pod security
```

## Management cluster

The management cluster is an appliance: it runs Cluster API, its providers and Kubehenge, and no workloads of anyone's. Rancher, monitoring and everything else users run go into the clusters it creates. Keeping it bare keeps it small, keeps its attack surface to what Kubehenge needs, and means losing a workload cluster never touches the piece that repairs it.

It runs Talos Linux: an immutable operating system with no shell or SSH, configured and upgraded only through its API, which suits a machine nobody should log into. One control-plane node is enough for a lab; three make it highly available, with Talos's own virtual IP in front of the API server. Control-plane nodes also run Kubehenge's controllers, so there are no separate workers. The Talos Image Factory builds a release's installer and disk image again with different bytes, so neither can be pinned by a digest that stays valid: the nodes pull the installer, Sidero's images and everything from registry.k8s.io only with their publishers' keyless signatures (Talos's `ImageVerificationConfig`), as they pull the Talos providers' images only with the signature of their fork's release workflow at a version tag, and the disk image, for which the factory publishes no checksum or signature, is downloaded over TLS alone.

Cluster API's providers are installed by the Cluster API Operator, so each provider and its version is a Kubernetes object that the Terraform/OpenTofu configuration declares, and upgrading a provider is changing a version number. The operator does not download a provider itself: a hook of the providers' release (`kubehenge manifests`) downloads each provider's metadata and components from its release, checks them against the SHA-256 `versions.tf` names for that version, and stores them in the ConfigMap the provider's `fetchConfig` selects. Each runs its release's own image, by the digest `versions.tf` names, with two exceptions while they last: capmox v0.9.1 runs as built by Kubehenge's release from a later upstream commit carrying a fix kubeadm upgrades need, with fixes of Kubehenge's own (`capmox_build` in `management-cluster/versions.tf`), and the Add-on Provider for Helm v0.6.4 with a fix that keeps it from creating a cluster's release twice (`helm_addon_build`). Both are built reproducibly, so the published images can be rebuilt from their sources and compared ([releasing.md](releasing.md)); a release of each that carries its fixes replaces the build. Talos's two providers come from Kubehenge's own forks of them, [cluster-api-bootstrap-provider-talos](https://github.com/kubehenge/cluster-api-bootstrap-provider-talos) and [cluster-api-control-plane-provider-talos](https://github.com/kubehenge/cluster-api-control-plane-provider-talos): Sidero Labs' releases are on Cluster API's v1beta1 contract, which Cluster API's core removes, and its control-plane provider has no `TalosControlPlaneTemplate`, which a ClusterClass needs. The forks carry both, with fixes of their own; they are maintained primarily for Kubehenge and open to anyone who runs Talos with Cluster API. Their releases are installed like any other, their files and images by the digests `versions.tf` names, and each fork's release workflow signs its image keylessly and attests the build provenance of its image and files; `make verify-providers` checks all of it in CI before a new pin is merged. `capmox` signs in to Proxmox VE with an API token of its own, created for it with only the privileges it needs. cert-manager's chart is pulled from its OCI registry by digest; the operator's comes by version from its project's HTTP repository, the only place it is published, with nothing Helm checks it against, while the operator's image is named by digest.

Every distribution's providers are installed, but their controllers run only while a cluster uses that distribution. Without one, Kubehenge's controller scales their Deployments to none, so a management cluster that only ever builds RKE2 clusters spends no memory on kubeadm's, k3s's or Talos's controllers. The eight take about 50 MiB each, about 400 MiB in all. When the first cluster of a distribution is created, the controller scales them up. Once they serve, it applies the distribution's control-plane and bootstrap templates, which their webhooks have to admit; Cluster API holds the new cluster until then, which adds a minute or so to the first cluster of each distribution. When the last cluster is gone, the controller removes the templates, then scales the providers back to none. All the controller may do to the providers is change their replica count, through the Deployments' `scale` subresource; the Operator leaves that count alone because the configuration removes it from the providers' manifests.

## ClusterClasses

One ClusterClass per distribution: kubeadm, RKE2, k3s and Talos. Each takes the same small set of variables (Kubernetes version, control-plane and worker counts and sizes, Proxmox VE nodes, storage and bridge, node addresses, control-plane virtual IP, add-ons) so that creating a cluster is a few lines whichever distribution it uses. Each wires in the always-installed set and passes the end-to-end suite before it is called supported (`testing.md`). They ship in the `kubehenge` Helm chart (`charts/kubehenge`), which the management cluster's configuration installs. The chart creates each ClusterClass and its Proxmox VE templates directly. Its control-plane and bootstrap templates go into a ConfigMap named after the class, which the controller applies while a cluster uses the distribution.

The Talos class takes one variable more, `talosVersion`, the Talos release the nodes run. Its control planes hold the endpoint with Talos's own virtual IP rather than kube-vip, and its machine configuration is the strategic patches the Talos bootstrap provider applies to what it generates: the same audit policy, admission configuration, authentication configuration and patient leader election as the other classes, serving certificates the cluster CA signs for the kubelets, and image signatures required as on the management cluster. The controller's external patch sets the configuration's `talosVersion` to the minor version of the release the machine boots first, so that each machine is generated in the schema its first release reads. Talos keeps SELinux as it ships it.

Cluster API replaces a control-plane node by adding its successor first, in every distribution: kubeadm's and RKE2's control-plane providers remove one first only from three control planes up, k3s's never, and etcd could not lose its only voting member anyway. A cluster with one control plane so runs on two etcd members, each needing the other, from the moment the new one is promoted until the old one is removed, and its API stops while either stalls for longer than etcd's election timeout. k3s runs etcd in one process with the controller manager and the scheduler, which exit once they miss their leases' renewal, and with them that node's etcd member and the other's quorum. The classes therefore give the control planes' controller managers and schedulers the management cluster's leases (60 s, renewed within 40 s), as Kubehenge does every controller it installs into a cluster that exits on a missed renewal: the Cilium operator, the cloud controller managers and the CSI plugin's sidecars. An etcd stall of up to 40 seconds then passes without a restart; a cluster whose second member is gone for good does not recover by itself ([troubleshooting.md](troubleshooting.md#one-control-plane-unreachable-after-a-roll)).

## Each cluster's own corner of Proxmox VE

A workload cluster runs a cloud controller manager and a CSI plugin that talk to the Proxmox VE API, so a cluster holds Proxmox VE credentials. Those credentials reach that cluster's VMs and volumes and nothing else, so a compromised cluster cannot touch its neighbours or the management cluster. Within the cluster, only the cloud controller manager and the CSI plugin's controller hold them, and both run on the control-plane nodes only, so no worker ever has them. The cloud controller manager uses the nodes' own network, so it initialises new nodes before any CNI runs.

- **A pool per cluster**, nested under the workload pool: `<workload pool>/<namespace>.<cluster>`. Cluster API's Proxmox VE provider creates the cluster's VMs in it.
- **A user and API token per cluster**, with rights on its own pool only: reading its VMs for the cloud controller manager, and configuring their disks for the CSI plugin. A group all clusters' users belong to adds what they share: using space on the workload storages and reading the nodes. None of them can delete arbitrary volumes or change a storage's definition, unless the cluster runs the CSI plugin's newest release (below); none of them reads beyond its pool and the nodes unless the cluster asks for HA group labels (below).
- **A VM that owns the cluster's volumes**, in the cluster's pool and never started. The CSI plugin creates volumes under its VMID, so only this cluster's token may attach them, and deleting the cluster deletes its volumes with it.
- **Deleting a volume through its owner VM.** The CSI plugin deletes a volume through the storage, which Proxmox VE allows only with `Datastore.Allocate` on the whole storage: every volume on it, and its definition. Kubehenge's controller instead deletes the volume of each released persistent volume through the owner VM, as an unused disk of that VM, with the cluster's own token; the plugin then finds the volume gone and completes. Proxmox VE deletes a VM's unused disk on the node the VM is on, so for a volume on storage local to another node the controller first moves the owner VM there; it has no disks, so only its configuration moves.
- **The CSI plugin's release.** Every cluster runs the plugin's last release that works with `Datastore.AllocateSpace`; its newer releases read the storage's configuration, which takes `Datastore.Allocate`. Where the management cluster allows it (`cluster_datastore_allocate`), a cluster's `csi` variable can choose the newest release, and the controller then grants the cluster's user a role holding `Datastore.Allocate`, `Datastore.AllocateSpace` and `Datastore.Audit` on `/storage/<storage>`, unpropagated, and takes it back when the variable is switched off. The admission webhook and `BeforeClusterCreate` allow that only on a storage the cluster has alone: none of the management cluster's (passed to the controller by the chart), none the VM templates have disks on (recorded every 30 seconds on the ClusterClasses as `kubehenge.dev/template-storages`), and none another cluster uses; and they refuse any cluster on a storage another holds it on. The controller checks the same on every reconcile; when a check fails it takes the grant back, installs the earlier release and records a `DatastoreAllocateRefused` event.
- **HA group labels.** The cloud controller manager labels each node with the HA groups, or HA node-affinity rules, of its Proxmox VE node, which Proxmox VE lists only with `Sys.Audit` on `/`. Where the management cluster allows it (`cluster_sys_audit`), the module creates a group holding `Sys.Audit` on `/`, unpropagated, and a cluster's `ccm` variable can ask for the labels; the controller then adds the cluster's user to that group, and takes it out when the variable is switched off. Proxmox VE lets only `Permissions.Modify` on `/` grant anything on `/`, so the controller holds `User.Modify` on that one group instead. The admission webhook and `BeforeClusterCreate` refuse the variable where the management cluster does not allow it, and the controller records a `SysAuditRefused` event when it cannot grant it.
- **Volume snapshots.** The CSI plugin copies a volume for a snapshot, a restore or a clone with `POST /nodes/{node}/storage/{storage}/content/{volume}`, which Proxmox VE lets only `root@pam` call, signed in with its password; no token passes, so no grant of Kubehenge's can make it work. Where the management cluster allows it (`cluster_volume_snapshots`), the administrator stores `root@pam`'s password in the Secret `kubehenge-root-pam` beside the ClusterClasses, and a cluster's `csi` variable can ask for snapshots. The controller then hands that cluster's CSI plugin a configuration of its own, `kube-system/kubehenge-proxmox-root`, signing in as `root@pam` (the cloud controller manager keeps the token), runs the plugin's newest release with its snapshotter sidecar and a 5-minute timeout on every sidecar, above the plugin's own 4-minute wait for a copy, and installs the VolumeSnapshotClass `proxmox` and, except on RKE2, which runs its own, the external snapshotter's CustomResourceDefinitions and snapshot controller. The admission webhook and `BeforeClusterCreate` allow it only where the password is stored and on a storage of a type the plugin copies on, local to each node (published every 30 seconds on the ClusterClasses as `kubehenge.dev/snapshot-storages`); the controller checks the same on every reconcile, keeps the token and records a `VolumeSnapshotsRefused` event when a check fails. Switching it off removes those releases and the root configuration; the CustomResourceDefinitions stay, so that VolumeSnapshots left behind keep their volumes.

Kubehenge's controller, in the management cluster, creates all of this before Cluster API creates any VM: Cluster API asks it through a lifecycle hook (`BeforeClusterCreate`, Cluster API's Runtime SDK) and waits until it answers. It hands the token to the cluster through a ClusterResourceSet, installs the cloud controller manager and CSI plugin through the Add-on Provider for Helm, and removes the pool, user and volume owner once the cluster's VMs are gone. Removing the owner VM deletes its volumes on shared storage and on its own node; the controller deletes those on other nodes' local storage first, and waits while a node that may hold some is offline. Its own token may create pools under the workload pool, users in the clusters' group and ACLs on those pools, move and configure the VMs in the workload pool, use the workload storages as the clusters do, and nothing more; with `cluster_datastore_allocate` it also holds `Datastore.Allocate` on the workload storages the management cluster does not use, so that it may grant a cluster's user the role there, and with `cluster_sys_audit` `User.Modify` on the group holding `Sys.Audit` on `/`, so that it may add a cluster's user to it.

The controller also tells `capmox` where to put each cluster's VMs. Left to itself, `capmox` clones every VM onto the node holding its template when a cluster names no nodes, and places no VM at all while one node it names does not answer, which is when a cluster needs replacements most. So the ClusterClasses leave the nodes to an external patch the controller serves (`GeneratePatches`): the cluster's `allowedNodes` that are online, or every online node when it names none. Every 15 seconds the controller reads which nodes are online and records them on each Cluster (`kubehenge.dev/online-nodes`), which has Cluster API compute the topology again when the list changes.

The same patch has RKE2 and k3s nodes install their release from files they check, in place of their bootstrap providers' online install, which runs whatever install script and release a tag names on the day a node boots. Neither project signs its releases or images, so the first time a cluster uses a release, the controller reads its checksum file and its install script, records their SHA-256s in the ConfigMap `kubehenge-release-checksums`, and holds every later node of that release to them. A node downloads the script, the release and the airgap images of its core and its CNI, checks each against the recorded checksum file, and hands them to its bootstrap provider's air-gapped install, so it pulls none of the distribution's images.

Every 30 seconds the controller also records on the kubeadm ClusterClass the Kubernetes versions its token finds templates for in the template pool, for each node OS (`kubehenge.dev/kubeadm-versions`, as JSON), and on the RKE2 and k3s ClusterClasses the node OSes their templates are there for (`kubehenge.dev/node-os-templates`); on all three it records the builds of every node OS template line (`kubehenge.dev/node-image-builds`), which the same `GeneratePatches` reads to point each machine template at one build ([Images](#images)), and the storages the templates have disks on (`kubehenge.dev/template-storages`). On the Talos ClusterClass, whose nodes run Talos rather than a node OS, it records the Talos releases it finds templates of (`kubehenge.dev/talos-templates`). The interface offers those versions, and refuses a cluster whose template is missing, since Cluster API clones with its own token: the people who create clusters need no privilege on the template pool.

Placing a cluster by one of Proxmox VE's HA node-affinity rules takes reading the rules, which needs `Sys.Audit` on `/`. Where an administrator has the rules offered to cluster creators ([install.md](install.md#ha-rules-for-cluster-creators)), the controller reads them every 30 seconds with its own token, which holds that privilege already, and records each enabled rule's name and the nodes it allows in the ConfigMap `kubehenge-ha-rules`, leaving out the rules it keeps for clusters' Proxmox VE HA. The interface's account may read that ConfigMap only while the setting is on; the interface asks Proxmox VE with the user's own ticket first, and hands the recorded names and nodes only to a user it refuses who holds `VM.Allocate` on the workload pool or a cluster's pool.

With Proxmox VE HA switched on ([install.md](install.md#proxmox-ve-ha)), the controller also makes each joined control-plane VM of a cluster on shared storage an HA resource, and keeps two HA rules per cluster: a negative resource affinity among those VMs, sized to the nodes Proxmox VE's HA manager knows, and a strict node affinity to the cluster's nodes when it may use only some. It does so with a token of its own, since only `Sys.Console` on `/` may write HA configuration, and the cluster tokens never see it. Two things follow from HA moving VMs that Cluster API's Proxmox VE provider does not expect:

- **A pre-terminate hook** (`pre-terminate.delete.hook.machine.cluster.x-k8s.io/kubehenge-ha`) on each control-plane Machine holds its VM's deletion until the controller has taken the VM out of HA, as Proxmox VE refuses to delete an HA resource's VM.
- **Its VM's node.** The provider deletes a VM on the node it recorded, and takes Proxmox VE's answer for a VM that has moved to mean it is gone, which would leave the VM running. So when a VM has moved, the controller marks its ProxmoxMachine with the node it is on (`kubehenge.dev/proxmox-node`); the change has the provider look the VM up across the cluster and record its node, and the hook stays until it has.

## Images

Each distribution boots from a different VM template:

| Distribution | Template |
| --- | --- |
| kubeadm | the cluster's node OS with containerd, the kubelet and kubeadm preinstalled at one Kubernetes version, and its control-plane images, each checked against Kubernetes' release signature |
| Talos | Talos's own image of one release from the Talos Image Factory, with the QEMU guest agent; Talos is its own OS, so no node OS is chosen |
| RKE2, k3s | the cluster's node OS with the distribution's SELinux policy; the distribution installs at boot from checked files |

`kubehenge template create` (or the Administration page in the appliance, with an administrator's session) fetches the image, prepares it by booting it once where it needs more, and turns it into a template `capmox` selects by its tags, all through the Proxmox VE API. Details: [templates.md](templates.md).

### Node OSes

The operating system under RKE2, k3s and kubeadm is a node OS, which each cluster chooses with its `nodeOS` variable: AlmaLinux 10 by default, or Rocky Linux 10, both in image mode, with openSUSE Leap 16.1 Immutable to follow once openSUSE releases it. Everything that differs between them lives behind one interface in `pkg/templates`, a family with its releases: where its image comes from and how its signature is checked, the signing keys of the repositories a build adds, how a template is made of it (its recipe), the CPU type it needs at the least, and what its nodes enforce. Every family enforces SELinux.

- **Image mode** (AlmaLinux, Rocky Linux): the build VM boots the family's cloud image, composes a minimal root file system from the family's signed repositories with `bootc-base-imagectl`, adds what a node of the distribution needs in a container build, checks the result with `bootc container lint`, and installs it with `bootc install` onto the template's own disk, which then boots once on its own for its first-boot checks. The node's `/usr` is read-only, and its automatic updates are off: a new build of the template replaces the nodes instead.
- **Transactional** (openSUSE Leap Immutable): the build VM boots the image itself, installs what a node needs as one new snapshot with `transactional-update`, and reboots into it; its automatic updates and reboots are off for the same reason.
- **The node OS in the patch.** `GeneratePatches` points each machine template at the cluster's node OS's template line (the tag `os-<family>-<release>`), and has RKE2 and k3s start with SELinux; clones keep their template's CPU type. Changing the variable rolls the nodes as an upgrade does. The controller places a cluster only on the online nodes whose CPU reaches its node OS's level (read from each node's CPU flags), a Talos cluster on those that reach `x86-64-v2`, the CPU type of Talos's templates, and its admission webhook refuses a node OS none of the cluster's nodes can run, or one that is not released. Talos clusters have no `nodeOS` variable: Talos is its own OS.

### Node image refresh

A node OS template is a line of builds, each tagged with when it was made, and every week a CronJob in the management cluster (`kubehenge template refresh`) makes a new build of each line, so the nodes get their node OS's updates by being replaced rather than patched in place, as Cluster API expects of immutable machines:

- **Which build a machine clones** is decided by the cluster's node image time (the annotation `kubehenge.dev/node-image`, the cluster's creation until it first moves): `GeneratePatches` sets each machine template's tag selector to the newest build of its line made by then and at least the soak old (24 hours by default, `--node-image-soak`). So the same cluster gets the same build on every reconcile, scale-up and repair, and a new build changes nothing until the time moves.
- **The time moves** in two places: the upgrader, which looks at every cluster every five minutes, sets it to now when the cluster is settled inside its maintenance window and a newer build has soaked, unless the cluster's `upgrades.nodeImages` is false; and the `BeforeClusterUpgrade` hook, so that any Kubernetes upgrade takes the newest builds with it. Cluster API then rolls the nodes as for an upgrade. Outside the window, the upgrader records its decision to hold the cluster, the build that waits and when the window opens, in the annotation `kubehenge.dev/node-image-held`, which the interface shows.
- **The refresh** holds a Lease so that one run builds at a time, builds each line, and then deletes what nothing needs: all but the two newest builds of a line, keeping any a cluster's node image time picks and any a ProxmoxMachine still waiting for its VM selects. It writes how it went to the ConfigMap `kubehenge-template-refresh`, which the interface shows.
- **Build now and creators' requests** go through the ConfigMap `kubehenge-template-requests`: the interface may only write a request there, and the controller starts the CronJob's Job for it, with `--missing` for a template a cluster creator asked for. The interface never holds the builder's token.
- **Its own token.** The refresh signs in to Proxmox VE with a user and token of its own, which may build and delete VMs in the template pool and nothing else of the clusters' or the management cluster's ([install.md](install.md#what-the-template-builds-may-do)).

### Talos upgrades

Talos nodes are outside this: Talos updates itself, so a Talos cluster's templates have no builds and its nodes are upgraded in place rather than replaced. Each release's template stands for a build of its minor version's line instead: the refresh keeps the two newest releases of each minor, and any older one a cluster's new machines boot or its nodes are upgraded to, a machine still being created selects, or someone asked for in that run, and deletes the rest.

- **Which template a machine clones** is the Talos release the cluster records for its new machines (`kubehenge.dev/talos-image`): `talosVersion` when the cluster is created, moved to the current `talosVersion` by the `BeforeClusterUpgrade` hook once that release's template is in the pool, since a Kubernetes upgrade replaces every machine anyway. A new machine boots that release and is then upgraded like the others, so changing `talosVersion` never rolls the cluster.
- **The in-place upgrade.** When a node runs another release than `talosVersion`, the controller upgrades it through the Talos API with the cluster's talosconfig, one node at a time, control planes first: it pulls the release's installer, has Talos install it to the inactive partition, drains the node (five minutes at most; a node whose pods do not all leave is rebooted anyway, with a warning event), reboots it and uncordons it once it is Ready on the new release. Talos moves a minor version at a time, so a jump of two goes through the newest release of the minor in between. Progress and the last upgrade are recorded on the Cluster (`kubehenge.dev/talos-upgrading`, `kubehenge.dev/talos-upgraded`), which the interface shows.
- **A failed upgrade** stops the rest: a node that does not come back Ready, or comes back on its old release because Talos rolled back to the other partition, is recorded in `kubehenge.dev/talos-upgrade-failed`, and the controller upgrades nothing more in the cluster until an operator removes it (**Try again** on the cluster's page).
- **Automatic patch upgrades.** Where the cluster's `upgrades.nodeImages` is on, the upgrader moves `talosVersion` to the newest patch release of its minor version inside the maintenance window, as node image refreshes bring the other distributions' nodes their updates. Talos releases get no soak time, and a new minor version is always an operator's choice.

## Add-ons

Add-ons are Helm charts installed per cluster by the Cluster API Add-on Provider for Helm, chosen when a cluster is created or later.

| Add-on | What | Release |
| --- | --- | --- |
| Rancher | runs in a cluster Kubehenge creates for it; Kubehenge registers its other clusters with it, so they appear in Rancher's interface | first |
| Headlamp | Kubernetes web UI per cluster | first |
| Monitoring | Prometheus, Alertmanager and Grafana per cluster, with kube-prometheus-stack's dashboards and alerts | first |
| Logs | Loki per cluster, fed by Grafana Alloy on every node or through the Kubernetes API, read in monitoring's Grafana | first |
| Backups | Velero backing up each cluster's resources and volumes to an S3 store an administrator set, encrypted with the cluster's own keys, and restoring them | first |
| etcd snapshots | the cluster's etcd taken by Kubehenge's controller into the same stores, encrypted with the cluster's own key, and restored on the control-plane nodes | first |
| Pod security | a Pod Security Standard level enforced by Pod Security Admission, by Kyverno's policies, or both | first |
| CIS hardening | the rest of the CIS Kubernetes Benchmark, beyond the baseline every cluster gets, with RKE2's own CIS profile | first |
| Istio | Istio in ambient mode per cluster: mutual TLS between the pods of the namespaces enrolled, without sidecars | first |
| Cilium Cluster Mesh | connects the pod networks of clusters that run Cilium | first |
| Load balancer | addresses for Services of type `LoadBalancer`, with MetalLB or kube-vip ([Networking](#networking)) | first |
| Certificates | cert-manager with an ACME issuer (DNS-01 or HTTP-01) or a CA of the cluster's own, and a default certificate for Traefik and its Gateway | first |
| GitOps | Argo CD or Flux per cluster, keeping it in step with a directory of a Git repository | first |

Kubehenge's controller turns a cluster's add-on variables into HelmChartProxies beside the cluster, and deletes the proxy when an add-on is switched off, which uninstalls it. Values never carry a secret: the Add-on Provider for Helm keeps them in plain text. Every chart is pinned by its digest, which a proxy's version carries as `<version>@sha256:<digest>`: Kubehenge's build of the Add-on Provider for Helm pulls an OCI chart by its manifest digest and checks that the version's tag points to it, and checks a chart from an HTTP repository against the SHA-256 of its archive that the repository's index lists. The images the charts run are pinned the same way: each chart's entry in the controller chart's values carries values that name every image by tag and digest, which the controller lays beneath its own. The images the Tigera operator deploys Calico from are pinned by an ImageSet named for its release, applied with Calico's Installation.

**Headlamp** (`headlamp: {enabled: true}`) has no rights of its own: its service account is bound to no role, and everyone signs in with their own token or through OIDC, so Headlamp shows each user exactly what their credentials allow. `access: view` binds its service account to Kubernetes' built-in `view` ClusterRole through the chart's own ClusterRoleBinding and starts Headlamp with `-unsafe-use-service-account-token`: Headlamp then sends every request with the account's mounted token, which the kubelet renews, and drops any token a user gives it, so everyone who reaches it reads what `view` allows (no Secrets, nodes or other cluster-wide objects but namespaces) and nobody changes anything through it. Switching it back to `token` removes the binding with the next Helm upgrade. It is not exposed: `kubectl -n headlamp port-forward svc/headlamp 8080:80` reaches it from a workstation, and `hostname` adds an Ingress on the cluster's ingress controller (RKE2 and k3s bring Traefik; Kubehenge installs it into kubeadm clusters), with the certificate from `tlsSecret`, or one from the certificates add-on while it is on, or the controller's default. Plugins are those in its image; nothing is fetched at run time. Its pod meets Pod Security's restricted level.

**Monitoring** (`monitoring: {enabled: true}`) installs kube-prometheus-stack into the `monitoring` namespace, with cert-manager, and every scrape is authenticated and verifies its server; nothing that serves metrics without authentication is opened beyond its node's loopback interface:

- **etcd, kube-proxy, the controller manager and the scheduler** serve their metrics on loopback only, as the CIS benchmark asks of the last two. A kube-rbac-proxy in front of each, on the node's address and the component's own port, takes only Prometheus's client certificate and asks the API server whether it may read `/metrics`. etcd and kube-proxy serve plain HTTP; the controller manager and the scheduler serve HTTPS, which their proxies verify against the cluster CA for `localhost`, and let `/metrics` through on loopback without credentials. On RKE2 their certificates come from the server CA; kubeadm's would be signed anew on every start by a CA of their own, so the class gives each control-plane node certificates from the cluster CA instead. Prometheus gets no etcd client certificate, which would give it every key in the cluster. On k3s every component runs in one process, whose kubelet already serves all their metrics, so Prometheus takes them from the kubelet, as Rancher does, and the chart's alerts look for them there. On Talos the controller manager and the scheduler serve with certificates they sign themselves, which Talos keeps inside their pods and gives no way to replace, so no proxy could verify them: until Talos passes them a serving certificate of the cluster CA, they go unscraped, and their alerts with them. The controller looks at their static pods' arguments, and once every one of them is passed `--tls-cert-file` it scrapes them through proxies as on kubeadm, with no change to the class.
- **Kubelets** on kubeadm ask the cluster CA for their serving certificates, which Kubehenge's controller approves when they name only the node and its Machine's addresses; the API server verifies them too. RKE2 and k3s sign theirs with the server CA.
- **node-exporter** listens on loopback behind its chart's kube-rbac-proxy, which takes the same client certificate. It reads the host's namespaces and file system, which only Pod Security's privileged level allows, so it has a namespace of its own labelled privileged; the rest of the add-on meets the restricted level.
- **Certificates:** cert-manager runs a CA of the add-on's own (ClusterIssuer `kubehenge-metrics`), which signs the proxies' serving certificates and Prometheus's client certificate, and nothing else. The chart's long-lived token is sent only to what asks for one, never over plain HTTP.

Prometheus keeps ten days of metrics on a 20 GiB volume from the cluster's default storage class, Alertmanager its silences on 1 GiB. `hostname` serves Grafana through the cluster's ingress controller, with the certificate from `tlsSecret` or the controller's default; without it, `kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80` reaches it. Its `admin` password is generated into the `kube-prometheus-stack-grafana` Secret. The release carries the proxies and certificates, so switching monitoring off removes them with it.

**Logs** (`logs: {enabled: true, collector: node|api, retentionDays: 7, sizeGiB: 10}`) need monitoring, whose Grafana reads them; the validating webhook and the interface refuse them without it, and refuse switching monitoring off under them. Loki runs as one binary in the `logging` namespace, its chunks and index on a volume from the cluster's default storage class that is kept when logs are switched off and only grows. Loki deletes logs by age, after `retentionDays`; nothing deletes them by size, so `sizeGiB` has to hold the days kept. Loki listens on loopback only, behind a kube-rbac-proxy on its pod's address that serves a certificate from the monitoring add-on's CA, authenticates every client, by a client certificate from that CA or a token, and asks the API server whether it may push (Alloy's user may) or read (Grafana's user may); a NetworkPolicy lets only Alloy's and Grafana's pods reach it. Grafana gets Loki as a data source with its own client certificate. Grafana Alloy collects them. One Alloy Deployment in `logging`, meeting the restricted level, keeps the cluster's events, which the API holds for an hour only; the pods' logs come from one of two collectors:

- **`node`**, the default: a second Alloy release, a DaemonSet in `logging-node`, which is exempt from pod security, since it runs as root to read the host's files. It mounts the pod log directory and the journal read-only, and the directory of the distribution's API server audit log, and keeps its read positions in a host directory so that a restarted collector neither loses nor repeats lines. Reading the files on the node gives it the logs of pods that end within seconds, every unit's journal and, on the control planes, the audit log. It holds no Kubernetes rights and no ServiceAccount token: the log files' paths name the namespace, pod and container. Talos has no journal: its services' logs are in memory, and the class has Talos send them, and the kernel's, as JSON lines over TCP to `127.0.0.1:5170` (`machine.logging.destinations` and a `KmsgLogConfig`), where the collector listens through a host port with Alloy's `otelcol.receiver.tcplog`, an experimental component its stability level is raised for. A NetworkPolicy lets nothing else reach the port, so only the node's own Talos can send to it; the lines arrive under `job="talos"` with the service as `unit`, `kernel` for the kernel's. Talos keeps the audit log in a directory only the API server's own user may enter, so there the collector holds `DAC_READ_SEARCH`, its one capability, over what it mounts read-only.
- **`api`**: the Deployment in `logging` reads the pods' logs through the API server too, with rights to list pods and read their logs, and needs nothing of the host. It is lighter, but misses the journal, the audit log, and a pod that ends before it starts following it.

Switching the collector installs or uninstalls the DaemonSet and changes the Deployment's configuration; switching logs off uninstalls Loki and Alloy and takes Grafana's data source away.

**Backups** (`backups: {enabled: true, target: …}`) installs Velero with its AWS plugin into the `velero` namespace, backing up on the cluster's schedule to one of the S3 targets an administrator set (the chart's `backupTargets`, which the ClusterClasses carry in the annotation `kubehenge.dev/backup-targets`), under `<prefix>/<namespace>.<cluster>/velero`. Velero's file-system backup reads every pod's volumes with Kopia, file by file, so it works on any storage, without snapshots:

- **Keys of the cluster's own.** Kubehenge's controller makes the cluster's keys once, when backups or etcd snapshots are first switched on, and keeps them beside the Cluster in the Secret `<cluster>-backup-keys`: an age identity its etcd snapshots are encrypted to (below), a 32-byte SSE-C key, with which the store encrypts every object Velero writes and which the plugin sends with every request, and the password of the cluster's Kopia repository, which encrypts the volumes' data before it leaves the node. The keys never reach the store, so its operator, or anyone with an access key that reaches the bucket, reads nothing of a cluster's backups. They are never changed, since the backups made with them can be read with nothing else, and the Cluster does not own their Secret: a cluster made again under the same name reads the backups of the one before, and deleting the Secret makes them unreadable for good.
- **Put in before Velero.** The controller writes the keys and the store's access key into the workload cluster's `velero` namespace before the chart installs, never into values. Velero would otherwise make its repository password itself, the same for every installation.
- **Access keys.** Velero signs in to the store with the cluster's own credential, typed into the interface, else the one an administrator stored for every cluster, or, with `existingSecret`, a Secret the cluster's owner keeps in the `velero` namespace. The controller reads credentials when it reconciles the cluster, with no watch on Secrets, so a new or replaced one reaches Velero within ten minutes. One access key for every cluster is the least work, at a cost: every cluster's Velero can then reach the others' folders, though not read them; a key per cluster, which the store limits to its folder, keeps clusters from deleting each other's backups.
- **What is left out.** `kube-system`, which holds the cluster's Proxmox VE token, `kube-public`, `kube-node-lease`, Velero's own namespace and those of the add-ons, which Kubehenge installs again itself and whose restored copies would fight the releases that own them; and what each node, the API server and the CNI keep of themselves: nodes, events, leases, CSR, volume attachments, and Cilium's and Calico's addresses and identities. emptyDir volumes are skipped.
- **Rights.** Velero's server runs without root or capabilities, at Pod Security's restricted level, but as `cluster-admin`, which backing up and restoring every resource needs. Its node agents read every pod's volumes as root through a hostPath of the kubelet's directory, so the `velero` namespace is exempt from pod security, as the CNIs' are. Its metrics, served without authentication, are off.
- **The interface's identities.** Two of the interface's identities in the cluster ([Interface](#interface)) live in the `velero` namespace, only while backups are on, each with a Role over Velero's own resources and nothing else: `kubehenge-backups` lists backups and restores and starts a backup, for everyone who may see or change the cluster; `kubehenge-restores` starts a restore, for those who may download the admin kubeconfig, since a restore writes whatever the backup holds, Secrets and RBAC among it. Neither reads a Secret.
- **Switching it off** removes the release, then Velero's resources, with their finalizers taken off, its CRDs and the `velero` namespace with the keys in it. The backups stay in the store and the keys beside the Cluster, so switching backups on again reads them.

**etcd snapshots** (`etcdSnapshots: {enabled: true, target: …}`) are taken by Kubehenge's controller itself, with nothing installed in the cluster, into the same targets under `<prefix>/<namespace>.<cluster>/etcd` ([clusters.md](clusters.md#etcd-snapshots)):

- **Reaching etcd.** Every control-plane provider keeps the cluster's etcd CA beside the Cluster (`<cluster>-etcd`: kubeadm's etcd CA, RKE2's and k3s's etcd server CA). For each snapshot the controller signs a P-256 client certificate from it in memory, valid for an hour and never stored, and reaches one member through the workload cluster's API server, as Cluster API's control-plane providers check etcd: a port-forward to the member's static pod on kubeadm and RKE2, and to the k3s provider's `etcd-proxy` pod on k3s, which forwards to the server's own etcd. The member's serving certificate is checked against the same CA for `localhost`, a name every distribution's carries. The API server sees only the forwarded bytes, which are TLS between the controller and etcd. No etcd key and no access key to the store reaches the workload cluster, unless the cluster opts into the distribution's own upload (below). On Talos, etcd runs as a Talos service rather than a pod: the controller asks a control plane's Talos API for the snapshot, with the talosconfig the Talos bootstrap provider keeps beside the Cluster (`<cluster>-talosconfig`), and records no revision, which Talos does not report.
- **Streaming.** etcd's snapshot stream goes straight into an S3 multipart upload in parts of 8 MiB, encrypted on the way with age to the cluster's identity, so a database of any size takes the same few buffers in the controller. etcd ends the stream with the SHA-256 of what it sent, which the controller checks before keeping the object; one cut off is deleted. The object's metadata then gets the database's SHA-256 and size, with the Kubernetes version, distribution and etcd revision. One snapshot runs at a time across clusters, each cluster a few minutes after the schedule's time of its own, and a failure is retried after 15 minutes, with a `Warning` event and the cluster's condition `EtcdSnapshotSucceeded` saying why. The newest `keep` stay; older ones are deleted after each snapshot.
- **Restoring.** A restore is asked for with the annotation `kubehenge.dev/etcd-restore` on the Cluster, which the interface sets for those with `Sys.Modify` on the cluster's pool, and is recorded step by step in `kubehenge.dev/etcd-restore-status`. While it runs, the controller changes nothing else of the cluster and takes no snapshot of it, and Cluster API is paused for it. The steps run as root scripts through the QEMU guest agent, with the restore token ([install.md](install.md#etcd-restores)) only: the controller decrypts the snapshot, stores it for the node encrypted again as `openssl enc -aes-256-ctr -pbkdf2` reads it, with a random password for that restore, and has the node fetch it from a presigned link that expires within the hour, check it against the SHA-256 the snapshot was taken with and delete the copy. Each script reads all of itself before running, so a restart of the API server or the guest agent midway leaves no half-run step, and every step is safe to run again. A restore that fails before etcd's database was swapped starts every control plane as it was; one after finishes the restore, which a marker on the node tells apart; and one the controller restarted in is finished or undone by the step it had reached. Without the restore token the interface writes out the same scripts as steps to run by hand. A Talos cluster is restored through its nodes' Talos API with its talosconfig, needing no restore token, as Talos recovers etcd: the controller reads the whole snapshot and checks it against its SHA-256 before anything changes, resets every control-plane node with its `EPHEMERAL` partition wiped (etcd's data with it, the machine configuration kept) and waits for each to boot again, streams the snapshot to the first once its etcd waits to be bootstrapped, checking it on the way, and bootstraps etcd there from it. The other nodes join the restored etcd by themselves, so no machine is replaced but one whose Talos API did not answer. Once any node may have been wiped, only the snapshot brings etcd back, so a restore that fails from there, or that the controller restarted in, is tried once more from the start.
- **The distribution's own upload.** On RKE2 and k3s, `distributionUpload: true` beside `enabled` also has the servers upload the snapshots they take themselves, to the same target under `<prefix>/<namespace>.<cluster>/<distribution>-etcd`. A patch of the class writes a configuration drop-in, `60-kubehenge-etcd-s3.yaml` in the distribution's `config.yaml.d`, with `etcd-s3`, the schedule, the number kept and `etcd-s3-config-secret: kubehenge-etcd-s3`; the controller writes that Secret into the cluster's `kube-system`, of the type `etcd.k3s.cattle.io/s3-config-secret`, with the target's endpoint, bucket, folder, region, CA and access key, and TLS verification on. The servers read the Secret at each snapshot, so a new key or target reaches them without a restart, and the key never enters the bootstrap data. CAPRKE2's `etcd.backupConfig` is not used, since it puts the key into the bootstrap data, which lands on every server's disk and in its VM's configuration drive, and skips TLS verification unless told otherwise; the k3s provider has no such fields, so both distributions get the drop-in. The keys Secret `<cluster>-backup-keys` records with `kubehenge.dev/etcd-upload-installed` that the Secret was put into the cluster, so the controller removes it again when the upload goes off, and reaches no cluster that never had it. It removes it only once no control-plane Machine, one being deleted included, may still run with the drop-in: none whose bootstrap data writes it and none without bootstrap data yet, since a server not yet replaced in the roll reads the Secret on each scheduled snapshot. The distribution reads the schedule in UTC, counts the number kept across all servers together, and stores the snapshots as etcd wrote them; Kubehenge neither encrypts, lists nor restores them. The drop-in is part of the control plane's bootstrap, so switching the upload, or changing the schedule or number kept while it is on, rolls the control-plane machines.

**Istio** (`istio: {enabled: true}`) installs Istio in ambient mode, without sidecars: istiod into `istio-system`, and ztunnel and istio-cni on every node into `istio-node`. A namespace or pod labelled `istio.io/dataplane-mode=ambient` joins the mesh: istio-cni redirects its pods' traffic through the ztunnel on their node, which carries it to the other side's ztunnel over mutual TLS with each workload's identity, so Istio's policies by identity apply, such as a `PeerAuthentication` that requires mutual TLS or an `AuthorizationPolicy` by service account. ztunnel and istio-cni reach into the nodes' network namespaces, which only Pod Security's privileged level allows, so `istio-node` is exempt from pod security; istiod meets the restricted level. With Cilium, Kubehenge's own or RKE2's, Cilium's `cni.exclusive` is off while Istio is on, so that Cilium leaves istio-cni's plugin in place; since Cilium's agents read that only when they start, switching Istio on or off restarts them. Waypoints, Istio's layer 7 proxies, are Gateways of the class `istio-waypoint`, which istiod serves since every cluster has the Gateway API ([Networking](#networking)). Switching Istio off first removes the `istio.io/dataplane-mode` label from every namespace and pod and waits until istio-cni has taken every pod's redirection away, since a pod still redirected once ztunnel has gone reaches nothing; then it uninstalls the charts. Istio's CRDs stay, with any resources of them.

**Cilium Cluster Mesh** (`clusterMesh: {enabled: true, peers: [...]}`) links clusters of one namespace that run Cilium, on any of the three distributions: Kubehenge's own Cilium on kubeadm and k3s, RKE2's bundled one on RKE2, which Kubehenge configures through a `HelmChartConfig` the cluster's ClusterResourceSet applies. Two clusters are linked while both have the mesh on and list each other, so neither can pull the other in; a link lets each cluster's pods reach the other's, by address and through global services, and lets each read the other's pod names, labels and identities, which Cilium's network policies select by. Every cluster that runs Cilium has, from the start, its own name and a Cilium cluster id unique in its namespace (the annotation `kubehenge.dev/cilium-cluster-id`), fixed for its life, since changing either would restart every workload; and every new one gets a pod range that no other Kubehenge cluster uses, clear of the nodes' network, since a packet for a peer's pod would otherwise be taken for a local one. A link is refused, with a `ClusterMeshNotLinked` event that says why, while the ranges overlap, the ids clash or an endpoint is unknown.

With the mesh on, Cilium runs its clustermesh-apiserver, which peers reach on NodePort 32379 of the control-plane endpoint, and KVStoreMesh, which caches the peers' state for the agents. Kubehenge's controller writes the rest into `kube-system`: the certificates, the peers' endpoints and the users peers sign in as. Each namespace has a Cluster Mesh CA of its own, in the Secret `kubehenge-cluster-mesh-ca` beside its clusters, ECDSA P-256 and valid for ten years; its key never leaves the management cluster, so no workload cluster can sign a certificate for another. The certificates it signs are valid for a year and renewed with a third of that left. Each peer signs in as a user of its own, which may read the cluster's state and nothing else. A peer added or taken away changes those objects only, so nothing restarts; switching the mesh on or off upgrades Cilium and restarts its agents. On RKE2 with CIS hardening, whose profile lets only `kube-system`'s own pods reach the pods there, a NetworkPolicy lets the peers through to the clustermesh-apiserver.

**Certificates** (`certificates: {enabled: true, issuer: …, domain: …}`) installs cert-manager, held back like Traefik until the cluster has the Gateway API, with its Gateway API support on, and Kubehenge's controller writes the rest into the workload cluster with its admin kubeconfig once cert-manager answers:

- **The issuer**, ClusterIssuer `kubehenge-ingress`: ACME, Let's Encrypt's or another server, answering DNS-01 through one of cert-manager's DNS providers or HTTP-01 through an HTTPRoute on Traefik's Gateway; or a CA. cert-manager's default issuer is set to it, so an Ingress annotated `kubernetes.io/tls-acme: "true"` gets its certificate there.
- **The default certificate**, with DNS-01 or the CA: Certificate `kubehenge-ingress` in `kube-system` for `domain` and `*.domain`, ECDSA P-256, whose Secret Traefik's default TLS store and its Gateway's `websecure` listener (HTTPS, port 8443 behind the nodes' 443) serve. On kubeadm both are values of the Traefik Kubehenge installs; RKE2's and k3s's own Traefik reads them from the Secret `kubehenge-traefik` in `kube-system`, which the cluster's ClusterResourceSet keeps in step and the HelmChartConfig on the control planes names, so that the file there stays as it is and no change of certificates replaces a node. The add-ons' Ingresses take it where it covers their host name, and ask the issuer for a certificate of their own where it does not.
- **The cluster's CA**, with the issuer `ca`: the controller makes it in the management cluster, in the Secret `<cluster>-ingress-ca` beside the Cluster and owned by it, ECDSA P-256, valid for ten years, and name-constrained to `domain`, with every IPv4 and IPv6 address excluded, so that a client trusting it trusts no name outside the cluster's domain. A copy goes to `cert-manager`, where the issuer reads it. It stays while the add-on is switched off and on, and a new domain makes a new one. The interface hands out its certificate to whoever may see the cluster.
- **The DNS provider's credential**, a user credential (purpose `dns01`) the interface stores beside the Cluster, or the one stored for every cluster when the cluster sets `sharedCredential`, which needs `Sys.Modify`. The controller copies it into `cert-manager` (`kubehenge-dns01`), never into a chart's values. Secrets are not cached, so the interface stamps `kubehenge.dev/credentials-stored-at` on every Cluster using a credential when it stores or removes one, and the controller takes the change at once. `existingSecret` names a Secret of the cluster's own instead, which Kubehenge never reads.

The issuer records which CA or ACME server it stands for (`kubehenge.dev/issuer-identity`); when that changes, the controller deletes the Secret of every certificate the issuer issued, in any namespace, so that cert-manager issues each again rather than keep one another CA signed. The annotation `kubehenge.dev/certificates` marks a cluster while the workload cluster may hold these objects; switched off, the controller deletes them and lifts the mark, and cert-manager goes when neither monitoring nor Rancher needs it.

**GitOps** (`gitops: {enabled: true, engine: argocd | flux, repository: {url: …, revision: …, path: …}}`) keeps a cluster in step with a directory of a Git repository: the engine applies what the directory holds, plain manifests or a kustomization, and removes what goes from it. Argo CD goes into `argocd`, Flux into `flux-system`; both meet Pod Security's restricted level and come with NetworkPolicies of their own. Once the engine's chart is in, Kubehenge's controller writes the repository's credentials into the engine's namespace and the object that starts the sync: an Argo CD Application `kubehenge` that syncs automatically, prunes, heals what is changed by hand and retries without end, without the resources finalizer, or a FluxInstance `flux`.

- **Flux** is installed by the Flux Operator, from the Flux manifests inside the operator's image, at the version the controller chart names (`addons.fluxOperator.flux`): the operator's digest pins Flux and every image it names, and nothing is fetched from a moving tag. It runs Flux's source, kustomize, helm and notification controllers, which, like the operator, request 10m of CPU each rather than Flux's 100m, so that Flux fits beside the other add-ons on a worker with the least vCPUs. The Flux Operator is licensed under AGPL-3.0, and Kubehenge runs it unmodified, as its project publishes it.
- **Reading the repository:** `auth` is `none` for a public repository over HTTPS; `deployKey`, an Ed25519 key pair the controller makes for the cluster and its repository and keeps in the Secret `<cluster>-gitops` beside the Cluster, whose public half the interface shows, to add to the repository as a read-only deploy key (a new URL gets a new key, since a forge takes a deploy key for one repository only); `token`, a user name and read-only token over HTTPS, the cluster's `gitops` credential; or `existingSecret`, a Secret of the owner's own in the engine's namespace. Over SSH the engine trusts only the host keys in `knownHosts`, or, without them, those the controller read from the server the first time, of every key type it offers, and keeps in the same Secret; the interface shows their fingerprints to compare, and a server the controller cannot reach leaves a `GitOpsHostKeys` event. The engine gets its copy of the credentials as `kubehenge-repository` in `argocd` or `kubehenge-gitops` in `flux-system`, never in values.
- **Argo CD's interface** signs in through the cluster's first OIDC provider, as its client or `signIn.clientID`: a public client with PKCE, or, with `signIn.clientSecret`, a confidential one whose secret is the cluster's `oidc-client` credential or a Secret of the owner's own. Its local admin and its web terminal are off, Dex and notifications are not installed, and nobody has rights in it but the provider's groups in `admins`. `hostname` serves it through the cluster's ingress controller; without one, `kubectl -n argocd port-forward svc/argocd-server 8080:80` reaches it.
- **Flux's web interface** (`ui: true`) is the Flux Operator's, off by default. At `hostname` it shows every Flux object and the workloads they deployed, and lets those signed in reconcile, suspend and resume them. It signs in through the cluster's first OIDC provider with a client secret, which the operator reads from a Secret, and acts as the signed-in user, impersonating them with the provider's prefixes, so the cluster's RBAC decides what each may see and do. Flux's NetworkPolicies take connections in `flux-system` only from the namespace itself, so the controller adds one, `kubehenge-acme-http01-solver`, that lets cert-manager's HTTP-01 solvers there be reached on their port, for the interface's certificate under `acme-http01`.
- **Rights:** the engine applies whatever the repository holds with cluster-wide rights, so whoever chooses the repository holds what the admin kubeconfig gives; the interface asks `Sys.Modify` on the pool for it, as for the kubeconfig.
- **Switching** it off, or to the other engine, removes the engine and leaves what it deployed running. For Argo CD the controller deletes the ApplicationSets, orphaning their Applications, then the Applications without their finalizers, then the chart; for Flux it deletes the FluxInstance, on which the operator uninstalls Flux, then the chart. The engine chosen starts syncing only once the other has gone, so that two never fight over the same objects. The engines' CRDs go with them; the deploy key and host keys stay beside the Cluster, for switching on again.

**Pod security** (`podSecurity: {admission: …, kyverno: …}`) holds a cluster's pods to a [Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/), `baseline` or `restricted`, through either or both of two checks:

- **Pod Security Admission**, Kubernetes' own: every ClusterClass gives the API server an admission configuration whose default level is `admission`, for every namespace that labels no level of its own. Left at `privileged`, Kubernetes' own default, it enforces nothing; at `baseline` it also warns about and audits pods short of `restricted`. The configuration is a file on the control-plane nodes, so changing the level replaces them one at a time.
- **Kyverno**: `kyverno` installs Kyverno and its Pod Security Standards policies into the `kyverno` namespace. They hold every namespace to the level whatever its labels say, which Pod Security Admission cannot, since anyone who may label a namespace may lift its level; they deny a pod when Kyverno cannot be reached, and Kyverno's policy reports list what falls short. Switched off, the policies go first, then Kyverno.

Both leave alone the namespaces of the components that need the host's network, file system or privileges: `kube-system` (the cloud controller manager, the CSI plugin, Cilium, kube-vip and the distributions' own components), Calico's, node-exporter's, Velero's (`velero`, whose node agents read every pod's volumes), Istio's node agents' (`istio-node`), Alloy's node collectors' (`logging-node`) and those of Rancher's agents and controllers. The chart's `podSecurityExempt` lists them. A workload of one's own that needs more than the level gets its namespace labelled, and, with Kyverno, a PolicyException in the `kyverno` namespace, the only one Kyverno takes exceptions from, so that only those who may write there can grant one.

**The security baseline** of every cluster is the part of the [CIS Kubernetes Benchmark](https://www.cisecurity.org/benchmark/kubernetes) that costs workloads nothing:

- **Audit:** the API server logs who did what to which object, at the `Metadata` level, without request or response bodies, which would put Secrets and tokens into the log, and without health checks, leases and events. It keeps a month of it, in ten files of 100 MB at most.
- **Secrets encrypted in etcd:** RKE2, k3s and Talos encrypt them themselves; on kubeadm, Kubehenge's controller makes a secretbox key once for the cluster, in the Secret `<cluster>-encryption` beside the Cluster, which every control-plane node gets. It is never replaced, since Secrets written under one key cannot be read with another.
- **Requests without credentials** are refused on RKE2 and k3s; on kubeadm they reach only the API server's health checks and the `cluster-info` ConfigMap, which `kubeadm join` reads before it has any.
- **The API server** limits the rate of events a namespace, and the cluster as a whole, may write (EventRateLimit), does not extend projected ServiceAccount tokens past their hour, and has profiling off, as do the controller manager and the scheduler, which serve on loopback only ([monitoring](#add-ons) reaches them through proxies). It and the kubelets offer only forward-secret TLS 1.2 ciphers with authenticated encryption.
- **Nodes** run with the kernel settings the kubelet expects, and the kubelet refuses to start on others rather than change them; kubeadm's kubelet configuration and unit files are readable by root alone.

**CIS hardening** (`cis: true`), chosen when a cluster is created and fixed after, adds what costs workloads something:

- Pod Security Admission enforces `restricted`, whatever `podSecurity` says; the exempt namespaces stay exempt.
- Every container that sets no seccomp profile of its own runs under the container runtime's default.
- Exec, attach and port-forward sessions end after five idle minutes.
- RKE2 runs its own CIS profile: etcd runs as a user of its own, and the pods in `kube-system`, `kube-public` and `default` take connections only from their own namespace, DNS and a few of RKE2's own services aside. With monitoring on, Kubehenge's controller lets Prometheus through to CoreDNS's metrics.

The end-to-end tests run [kube-bench](https://github.com/aquasecurity/kube-bench) on a hardened cluster of each distribution, against the CIS Kubernetes Benchmark 2.0 for kubeadm and Rancher's own benchmarks for RKE2 and k3s, and fail on every failed check but one: kubeadm runs etcd as root, so its data belongs to root (1.1.12), and Kubernetes has no supported way to run kubeadm's etcd as another user. The benchmark's policies section is the cluster owner's, since it judges what runs in the cluster rather than how the cluster is built.

**Rancher** (`rancher: {install: true, hostname: …}`) goes into one cluster Kubehenge creates for it, never into the management cluster, together with cert-manager; Rancher makes its own CA, and its server URL is fixed to `hostname`, which must resolve to that cluster's ingress controller for people and for every registered cluster. Kubehenge's controller registers every other cluster with it once the cluster is available, unless the cluster sets `register: false`:

- It signs in to Rancher's cluster with the kubeconfig Cluster API keeps for it, so there is no Rancher account or token to look after.
- It creates the cluster's `provisioning.cattle.io` Cluster there, fetches the agent's manifest through that cluster's API server, and applies it to the registered cluster. The agent trusts only Rancher's CA, pinned by its checksum in the manifest.
- A cluster leaves Rancher before it is deleted (Cluster API's `BeforeClusterDelete` hook) or when `register` turns false, while Rancher can still clean up inside it. Rancher's own cluster first removes every registered cluster.

Rancher's chart refuses Kubernetes versions its release does not run on, so the controller refuses to create the Rancher cluster outside them and holds back an upgrade beyond them (`BeforeClusterUpgrade`) until a Kubehenge release brings a Rancher that runs there. On fewer than 4 vCPUs a node running Rancher starves its own etcd and API server, so `BeforeClusterCreate` refuses such a cluster, and a validating webhook on Clusters refuses switching Rancher on or making its nodes smaller later. Rancher's first admin password is generated into the `bootstrap-secret` Secret in `cattle-system`, never written into values.

Rancher runs with imported-cluster version management off, with which it would upgrade RKE2 and k3s itself beside Cluster API: Kubehenge creates and upgrades the clusters, and Rancher's upgrade jobs name their images by tag alone. The images Rancher starts itself (its agent, shell, webhook and Fleet) are named by digest through its chart's values. Rancher also installs Turtles, its own Cluster API, without which it never takes a registered cluster as ready. Rancher reads Turtles' values only from its `rancher-config` ConfigMap, which its chart writes without them, so Kubehenge's controller writes that ConfigMap into Rancher's cluster before the chart installs, with Turtles' image and its Cluster API controller by digest, and Helm adopts it as it installs.

## Cluster autoscaler

A worker pool whose topology entry carries Cluster API's `cluster-api-autoscaler-node-group-min-size` and `-max-size` annotations, and no replicas, is autoscaled: Cluster API copies the annotations to its MachineDeployment and leaves its replicas to whoever scales it. Kubehenge's controller runs one [cluster autoscaler](https://github.com/kubernetes/autoscaler/tree/master/cluster-autoscaler) per cluster with such a pool, on its Cluster API provider with auto-discovery of that cluster's MachineDeployments alone, and removes it once no pool is autoscaled or the cluster goes.

- **The release** is the one of the cluster's Kubernetes minor, since each carries that minor's scheduler to decide where pending pods would fit; a minor without one runs the newest earlier release, and a cluster older than all of them the oldest. The chart lists one image per minor, by tag and digest, and Renovate moves each within its minor only. In the management cluster they pull, as everything from registry.k8s.io does, only with the Kubernetes release signature.
- **Scale from zero.** A pool at none has no node to learn from, so the controller writes on its MachineDeployment what a new one holds (`capacity.cluster-autoscaler.kubernetes.io/cpu`, `memory`, `ephemeral-disk` and `labels`, by server-side apply under a field owner of its own): the class's cores, 90% of its memory and disk, the rest standing for what the node reserves for itself and its system pods, and the node labels Cluster API gives its Nodes. It keeps them in step with the pool's machine size.
- **Control planes** stay tainted while any pool may grow, so a workload never lands there only to be evicted once a worker comes.
- **Room.** The node addresses must hold the control planes, every pool at its most and one machine for a rollout; the validating webhook and `BeforeClusterCreate` refuse a change that makes a shortage worse. While a pool grows, the controller looks every minute for a worker whose VM Proxmox VE cannot place for want of memory and records `AutoscalerNoRoom` with the provider's reason; the autoscaler gives such a machine up after 30 minutes.

**Rights.** Each cluster's autoscaler has a ServiceAccount of its own in the `kubehenge-autoscaler` namespace, bound in its cluster's namespace to a ClusterRole that reads MachineDeployments, MachineSets, MachinePools, Machines and Proxmox machine templates, patches the MachineDeployments' `scale` subresource, and updates Machines, which it marks for removal. RBAC cannot narrow that to one cluster's objects, as all clusters of a namespace share it, so a ValidatingAdmissionPolicy does, for every autoscaler account: its parameter, the ConfigMap `kubehenge-autoscaler`, names for each account its cluster and the MachineDeployments of its autoscaled pools, which the controller writes before it binds the role and removes before the account; an account the ConfigMap does not name may change nothing, a scale only of a pool it names, and a Machine only of its cluster, with nothing but the removal annotation changed. Reads stay namespace-wide: an autoscaler sees the machines of every cluster in its namespace, which is the residual risk of the design. Inside the cluster it is the autoscaler identity, `kubehenge-autoscaler` in `kube-system` (see Identities inside the clusters), which reads what its scheduling simulation needs but no Secrets, updates Nodes and evicts pods to drain the workers it removes, writes events, and writes no ConfigMap but its own status in `kube-system`. Its tokens, the identity's and (placed inside) its management account's, kept in the cluster's `kube-system` the same way, last an hour and are renewed every 20 minutes. The chart creates the policy's ConfigMap empty: the API server looks a policy binding's parameter up before the policy's match conditions, so without it the binding would refuse every change of MachineDeployments and Machines, Cluster API's own included. What an autoscaler has in `kubehenge-autoscaler` (its Deployment, account, token Secret and policy entry) lies outside its Cluster's namespace, where owner references cannot reach, so the controller holds the Cluster with the finalizer `kubehenge.dev/autoscaler` before it makes any of it and lifts it once all of it is gone: a cluster deleted while the controller is down waits for it.

**Where it runs.** By default in the management cluster, which then holds the token into the cluster, as it holds the cluster's kubeconfig anyway, while the cluster holds nothing of the management cluster: 64 MiB requested each, with a limit of 512 MiB. The `autoscaler` variable's `placement: workload` runs it on the cluster's control planes instead, as a system-cluster-critical pod tolerating their taint, reaching the management cluster at the `managementEndpoint` the module sets; the cluster then holds a management cluster token that reads every cluster's machines in the namespace, so the interface asks for `VM.Audit` on the workload pool before it places one there.

## Interface

A web app in a small LXC container on Proxmox VE, installed with one line in the Proxmox VE shell. It is where Kubehenge starts and what looks after it:

- **First run:** a wizard creates the management cluster, through the same module `tofu apply` uses, with the signed-in administrator's own Proxmox VE session; no administrator token is stored.
- **Day two:** the container keeps the management cluster's state, encrypted, and runs its Talos and Kubernetes upgrades, its growth from one node to three, moves of its VMs to other Proxmox VE nodes, and repair. It keeps working while the management cluster is unwell, to show and fix it. It holds state, so it belongs in Proxmox VE's backups; the interface warns administrators while no enabled backup job includes it (by its ID, by its pool, or by all guests on its node).
- **Sign-in through the Proxmox VE API.** Every Proxmox realm works, PAM, Proxmox VE users, LDAP, Active Directory and OIDC included. No second user directory. A second factor is passed on to Proxmox VE as its own sign-in page would: TOTP, Yubico OTP and recovery keys. A WebAuthn key is bound to Proxmox VE's own address, so its users sign in through an OpenID realm or another factor. An OpenID realm sends the browser to its identity provider, which returns it to the interface (`/api/openid/callback` under `--public-url`, to be registered with the provider); Proxmox VE checks the code, and the interface accepts the return only in the browser that started it.
- **Sessions:** the Proxmox VE ticket stays on the server, in memory only; the browser holds a random session ID in a `__Host-` cookie (Secure, HttpOnly, SameSite=Strict) and every change also carries a per-session CSRF token. Proxmox VE renews a ticket without asking the realm or the second factor again, so a session ends after a fixed time (eight hours by default) however active it is. Failed sign-ins are limited per user and per address. The frontend loads no inline script or style, and the Content-Security-Policy allows none.
- **Permissions follow Proxmox VE's, by pool.** Each cluster has its own pool under the workload pool. Seeing a cluster needs `VM.Audit` on its pool; creating one needs `VM.Allocate` on the workload pool; scaling, upgrading, changing add-ons and deleting it need `VM.Allocate` on its pool; downloading its admin kubeconfig, and restoring one of its backups, need `Sys.Modify` there. Creating also needs what Proxmox VE asks of anyone creating a VM there: `Datastore.AllocateSpace` on the storage and `SDN.Use` on the bridge or VNet (on the VLAN, when one is set). Installing Rancher needs `Sys.Modify` on the workload pool, since Rancher receives the admin kubeconfig of every cluster that registers with it. The app asks Proxmox VE for the signed-in user's effective privileges on each path, then acts with its own account; administrators share clusters with the same ACLs they share VMs with. A cluster the user may not see is answered as not found. As everywhere in Proxmox VE, a role given to a user on a cluster's own pool replaces, for that pool, what the user inherits from the workload pool, so it has to hold `VM.Audit` too.
- **Namespaces:** the interface creates and changes clusters in `clusters`, and in the namespaces an administrator adds beside it (`extra_cluster_namespaces`, the chart's `interface.extraNamespaces`). The chart gives the interface's account a Role in each to create, change and delete Clusters and to read and write Secrets there, and lists them in the ConfigMap `kubehenge-interface` in `kubehenge-system`, which the interface reads; taking a namespace off the list takes the Role away and keeps the namespace and its clusters. Everywhere else the account reads only. Nothing else is per namespace: the controller, the credentials policy and the health identities work cluster-wide, a cluster's pool already carries its namespace (`<namespace>.<name>`), the ClusterClasses are referenced from `kubehenge-system`, the IP pools are made beside each cluster, and Cluster Mesh links clusters of one namespace, sharing that namespace's CA.
- **Credentials typed in.** What reaches a service outside the clusters needs a secret: a backup target's keys, a DNS provider's API token for DNS-01 certificates, a private Git repository's token, an identity provider's client secret. The interface stores each in a Secret beside its cluster, of the type `kubehenge.dev/user-credential`, named `<cluster>.<purpose>`, labelled with its purpose (`kubehenge.dev/user-credential`) and its cluster (`kubehenge.dev/credential-cluster`), and owned by the Cluster, so deleting the cluster deletes it.
  - **Who may set one:** storing, replacing or removing a cluster's credential needs `Sys.Modify` on its pool, as the admin kubeconfig does, since a credential reaches as far into what the cluster runs; seeing whether one is set needs what seeing the cluster does. A credential for every cluster, such as an administrator's backup target, is named `kubehenge-<purpose>` and needs the privileges on `/` that the management cluster's own settings need.
  - **Write-only:** the interface never hands a value back, only whether one is set, when, and by which Proxmox VE user (the annotations `kubehenge.dev/credential-set-by` and `kubehenge.dev/credential-set-at`). Replacing one takes every value again. The log records who changed which credential, never what it holds.
  - **Held to them:** RBAC cannot tell one Secret from another on create, so a ValidatingAdmissionPolicy in the chart (`kubehenge-interface-credentials`) holds the interface's account to these Secrets: it may create, change and delete only Secrets of that type, with a purpose it knows and the name that goes with it, and change or delete none without the label. A compromised or faulty interface cannot overwrite a cluster's kubeconfig, CA or Proxmox VE token, or make a Secret Kubernetes or Cluster API acts on, such as a ServiceAccount token. The policy runs inside the API server, so no webhook has to answer for it, and it fails closed. Anyone else, such as a GitOps tool, is not its concern.
  - **Without the interface:** clusters managed with GitOps or kubectl name a Secret of their own instead. Every feature that takes a credential also takes `existingSecret`, the name of a Secret the cluster's owner creates in the workload cluster, which never passes through the management cluster and needs no privilege of Kubehenge's.
- **Identities inside the clusters.** What the interface reads or starts inside a workload cluster, and what the cluster autoscaler does there, is done as one of Kubehenge's identities there: a ServiceAccount `kubehenge-<identity>` with a role for one job and nothing else, so that what serves one purpose cannot do another's whatever its holder does, and the workload cluster's audit log tells them apart. None may read a Secret or exec. Kubehenge's controller creates each identity a cluster has once the cluster's control plane is up and the identity's namespace exists, puts back what was changed of it, and asks the cluster for a one-hour token of it with the TokenRequest API, renewed every 20 minutes. The token is never stored in the workload cluster: it is kept, with the API server's address and CA, in the Secret `<cluster>-<identity>` beside the Cluster and owned by it, its expiry in the annotation `kubehenge.dev/token-expires`, so none outlives an hour once the controller stops renewing it. The autoscaler identity's Secret is the exception: an autoscaler running in the management cluster mounts it, and a pod mounts Secrets of its own namespace alone, so it is kept in the `kubehenge-autoscaler` namespace, labelled with its cluster, with a kubeconfig that reads the CA and the token from the files beside it, and goes when the cluster does. An identity a cluster no longer has, as the backup identities once backups are switched off, loses its Secret, and leaves the workload cluster with its namespace, the autoscaler identity with the autoscaler. The interface reads these Secrets only in its own namespace.
- **Health page.** One page says how a cluster stands: what needs attention first, then its nodes, unwell pods, waiting volume claims, add-on releases, what Cluster API reports and the last hour's events. Anyone who sees the cluster (`VM.Audit` on its pool) sees it, and it shows names, reasons and messages, never a spec, an environment or a Secret.
  - **From the management cluster:** the interface's own account reads the cluster's machines, MachineDeployments, MachineHealthChecks, control plane, HelmReleaseProxies and the events of its namespace, all read-only.
  - **From inside the cluster:** for clusters in the interface's namespaces, as two of the interface's identities in the workload cluster's `kube-system`: `kubehenge-health` may get and list nodes, pods, events and PersistentVolumeClaims and read `/readyz`; `kubehenge-health-logs` may only read pods' logs. Once their tokens run out, the page says since when its view is stale.
  - **Logs apart:** logs carry secrets often enough, so they take `Sys.Modify` on the cluster's pool, as the admin kubeconfig does, and come from the logs identity alone: the token behind every viewer's page cannot read a single line, whatever the interface does, and the workload cluster's audit log tells the two apart. The interface hands out the last 60 lines of one container at a time (the run before, for a container that crash-loops) and logs who read which.
  - **Cheap to keep open:** each cluster is read once for every viewer, at most every 10 seconds, with a deadline, list limits and the API server's cache; each VM's CPU line for the last hour comes from Proxmox VE with the viewer's own ticket, so it shows only the VMs that viewer may see.
- **What it does:** create, list, scale, upgrade and delete clusters; choose the distribution, add-ons, identity providers and automatic upgrades; download a kubeconfig; open each cluster in Headlamp, signed in where the administrator lets it; and, for administrators, build VM templates, upgrade Kubehenge, and apply, change or remove the management cluster.
- **Headlamp in the appliance:** one Headlamp, the appliance's own pinned copy (its server and frontend, taken from Headlamp's release and checked against its checksum when Kubehenge's release is built), serves the clusters of the interface's namespaces on port 8443, behind the interface's sign-in. Being a separate origin, no page it shows can run script where the interface's session lives.
  - **Its kubeconfig:** the interface writes each cluster's API address and CA there, never a credential, since Headlamp would use one for every visitor. Headlamp picks up clusters as they come and go. People sign in to each cluster with their own token, or through the cluster's identity provider (see Signing in to clusters), and Headlamp keeps it in an HttpOnly cookie for that cluster's paths only.
  - **Signed in for kubeconfig holders:** with the module's `headlamp_sign_in` (the chart's `interface.headlampSignIn`), off by default, the gate signs those who hold `Sys.Modify` on a cluster's pool, and may download its admin kubeconfig anyway, in as cluster-admin. Kubehenge's controller keeps two ServiceAccounts in the `kube-system` of each cluster in the interface's namespaces: `kubehenge-headlamp`, bound to `cluster-admin`, and `kubehenge-headlamp-issuer`, whose role lets it make `kubehenge-headlamp`'s tokens (`serviceaccounts/token` by that name) and nothing else; the issuer is one of the interface's workload identities, wanted while the sign-in is on and the cluster is in one of the interface's namespaces (the chart passes `interface.namespace` and `interface.extraNamespaces` to the controller), with its one-hour token beside the Cluster (`<cluster>-headlamp-issuer`) and renewed like the others'. On such a user's first request for a cluster, the interface has the cluster make a token of `kubehenge-headlamp` for that session, lasting an hour or until the session ends (ten minutes at the least, the TokenRequest API's shortest), keeps it in memory and sets it as the `Authorization` of that session's requests for the cluster, which Headlamp passes on when the browser holds no token of its own. The token never reaches the browser, so a script on Headlamp's pages cannot carry it off, and the gate checks the privilege again every 30 seconds. The interface logs each token it makes with the Proxmox VE user and the token's ID, which the cluster's audit log records with the ServiceAccount (`authentication.kubernetes.io/credential-id`). Switched off, the controller deletes the ServiceAccounts, `kubehenge-headlamp` first, which ends every token made for it at once, then the issuer's Secret. Headlamp's log out of a cluster posts to its `/encoded-clusters/<cluster>/clear-token`, which clears its token cookie; the gate passes it on and drops the session's token too, and signs the session in to that cluster no more until the session opens it from the interface again, whose links go through the gate's `/kubehenge/open/<cluster>` for that. The session's cookie is `SameSite=Strict`, so no other site's link signs anyone in again.
  - **Its actions:** with the module's `headlamp_actions` (the chart's `interface.headlampActions`, which the chart writes into the ConfigMap `kubehenge-interface` the interface reads every 30 seconds), off by default, the gate serves two of the plugins Headlamp ships, which the appliance carries: the Helm app catalog and the Prometheus charts (`/static-plugins/`, read only, and left out of Headlamp's plugin list while off). It passes on a cluster's Helm routes by exact method and path: its releases listed, one release and its history, an action's status, rollback, uninstall, install and upgrade, and the repositories and their charts listed. Headlamp acts there with the request's credentials, the user's own or the sign-in's. An install or upgrade must name a chart of a repository (`repository/chart`) and fetch no dependencies: Helm would also take a path on the appliance, an address or an OCI reference, and have the appliance read its own files or fetch from anywhere it reaches; Headlamp also runs in its own empty state directory, where no relative path names a chart. Headlamp keeps one list of repositories for every user and cluster, so only those who hold the setup's privileges on `/` add, update or remove one, over HTTPS with its certificate checked and its credentials sent to its own host alone. Port forwards stay refused: Headlamp offers them in its desktop app alone, and a forward would listen on the appliance's loopback for everyone signed in to the cluster. Node drain goes through a cluster's own `drain-node` route with the user's credentials either way; the routes that name the cluster in the request rather than its path stay refused, as do the external proxy, which the catalog's Artifact Hub search takes, and Headlamp's own metrics.
  - **Isolation:** the Headlamp server runs as a user of its own (`kubehenge-headlamp.service`, systemd's dynamic user) on the loopback interface. It can read nothing of the interface's state, and only the interface reaches it.
  - **Only while used:** Headlamp holds more of the appliance's memory than the interface itself, so it runs only while someone has it open. systemd listens on its port and starts it with the first connection (a quarter of a second). It stops again once no connection has been open for 15 minutes.
  - **The gate in front:** the interface takes the session cookie (host-only cookies reach every port) and strips its own cookies before passing a request on. It checks `VM.Audit` on the cluster's pool for every `/clusters/<namespace>.<name>/` request, rechecking every 30 seconds, and lists only those clusters. It refuses what a shared server must not offer: port forwards (they would open ports on the appliance), Helm, node draining, the external proxy, the WebSocket multiplexer, metrics, adding clusters or kubeconfigs, setting a token for others, and plugin changes.
  - **The add-on:** the in-cluster Headlamp add-on remains for a cluster that wants Headlamp at a hostname of its own.
- **Look:** it follows Proxmox VE's interface, so it feels part of it. Proxmox VE's own toolkit is GPL-licensed, so the look is Kubehenge's own theme, not borrowed code.
- **Built as:** a Go backend (`pkg/ui`, run by `kubehenge serve`), which uses the Cluster API and Kubernetes client libraries directly, serving a React and TypeScript frontend (`web/`) embedded in the same binary. The `kubehenge` command-line tool shares the backend's code. Clusters created here carry the creating user in the annotation `kubehenge.dev/created-by`, and every change is logged with the user who made it.

### Optional entry inside Proxmox VE

Proxmox VE has no supported way to extend its own web interface. An opt-in installer (`appliance/pve-entry/`) adds a Kubernetes entry that leads to the appliance:

- **What it adds:** a button beside Create VM and Create CT, and an item under Datacenter. Both open the appliance in a new tab, since the appliance refuses to be framed and stays an origin of its own.
- **How:** one line added to the page template `pve-manager` ships, loading a script of ExtJS overrides that runs before Proxmox VE builds its workspace.
- **Surviving updates:** an apt hook puts the line back after a `pve-manager` update replaces the template, and logs it. `--remove` returns the node to its packaged state.
- **Failing safe:** the script extends two of Proxmox VE's interface classes, which are no API. If a release renames them, or a step of the entry fails, the entry stays out and Proxmox VE's interface renders as shipped, with the reason in the browser's console.
- **Scope:** each node serves its own interface, so it is installed per node; `appliance/install.sh` asks whether to add it on the node it runs on. The appliance never depends on it.

## First run

Cluster API needs a cluster before it can create clusters. One Terraform/OpenTofu apply, or the appliance itself, creates a small management cluster on Proxmox VE VMs with everything above installed. From then on, clusters are created from the interface or from YAML.

The appliance (`appliance/install.sh`) checks everything it downloads against checksums it carries, creates an unprivileged Debian container, gives it a certificate signed by the Proxmox VE cluster's own CA, and runs the interface as an unprivileged user on ports 443 and 8443 (the shared Headlamp). Its first-run page runs the `management-cluster/` module with OpenTofu on the signed-in administrator's session: the ticket and CSRF token reach OpenTofu through its environment only, and the state is encrypted with a key derived from a passphrase the administrator chooses, which is not stored and is asked for again by every later apply, unless an administrator switches on automatic upgrades of the management cluster ([Upgrades](#upgrades)). The management cluster's admin kubeconfig and talosconfig stay inside that state, which an administrator can open from the Administration page with the passphrase for repairs the interface cannot make (every download is logged); the interface works with a ServiceAccount of its own that sees every cluster but changes clusters, reads their kubeconfigs and stores their credentials only in its namespace (`clusters`).

## Signing in to clusters

Every cluster accepts client certificates and ServiceAccount tokens, as Kubernetes does. Its `oidc` variable adds OpenID Connect providers whose ID tokens its API server accepts, up to eight, written as Kubernetes' structured authentication configuration (one JWT authenticator per provider). Each entry has:

- the issuer URL;
- the client ID, which a token's audience must name;
- the claims for user name and groups;
- prefixes, `oidc:` unless set, which may not start with `system:`;
- the scopes sign-in tools ask for;
- a CA, when a public one does not sign the provider's certificate.

- **The appliance-wide default.** Providers set on the Administration page, or as the module's `cluster_oidc` (the chart's `clusterOIDC`), are the variable's default. Every new cluster trusts them unless it sets its own list, and the create wizard starts from them. A change applies to clusters created afterwards.
- **Who may choose.** Whoever runs a provider can issue a token for any name, so a cluster may keep or drop the default's providers freely. Adding any other provider needs `Sys.Modify` on the pool, as the admin kubeconfig does: on the workload pool for a new cluster, on the cluster's own pool for a change.
- **Changing it.** Changing a cluster's providers replaces its control-plane nodes, as any change of the API server's configuration does.
- **Headlamp.** The shared Headlamp offers the first provider's sign-in beside the token prompt, as a public client with PKCE, so no client secret is stored. The provider must accept `https://<appliance>:8443/oidc-callback` as a redirect URL. The browser that starts a sign-in is the only one the gate lets finish it: it keeps a hash of the OAuth state in a short-lived cookie.

## Upgrades

**Kubehenge itself.** The appliance's Administration page shows the installed release and newer ones, and upgrades with a button; it can also upgrade automatically, once a day at a chosen hour, to new patch releases or to new minor releases of the same major version. The interface never replaces software itself: it drops a request into a spool, and a separate root service (`kubehenge-update`) carries it out. That service accepts only a release named in an index signed with Kubehenge's release key (Ed25519, built into each release, never configurable at run time), only one newer than the installed release, and only an archive matching the signed checksum; it swaps the files by rename and restarts the interface. A run of the management-cluster module holds a lock on the appliance's state directory, which the updater and `install.sh --upgrade` take too, so no upgrade restarts the interface in the middle of a run and no run starts during an upgrade; the kernel releases the lock when its holder ends, so a crash leaves none behind. The management cluster then moves to what the new release carries when an administrator applies it again from the same page. Every apply records the release that ran it, so the page says when the management cluster runs what an older release applied, and which component versions applying this one changes (read from the module's `versions.tf` and Kubehenge's chart).

**The management cluster on its own.** An apply needs the state passphrase and a Proxmox VE credential that can create users, roles, ACLs and VMs, and the appliance keeps neither by default. An administrator may switch on automatic upgrades of the management cluster, which then has the appliance keep the passphrase and the API token of a Proxmox VE user of its own, `kubehenge-upgrader@pve`, holding the Administrator role on `/`, in a file only the interface's user and root can read; the passphrase itself, since OpenTofu derives a new key for every state it writes, so no derived key could stand in. The interface then applies the saved settings with them in Kubehenge's upgrade hour, once the appliance runs a newer release than the one that last applied the management cluster, at most once a day. Switching it off deletes the file, then the user; so does removing the management cluster.

**Clusters.** The `upgrades` variable of every ClusterClass asks Kubehenge's controller to upgrade Kubernetes automatically: `patch` keeps the minor version, `minor` also moves to the next one, one minor at a time and never past the distribution's stable release (RKE2's and k3s's release channels; for kubeadm, the newest version a template has been built for; for Talos, Kubernetes' own newest release of each minor version, never one the cluster's Talos release does not run, and never while its nodes are being upgraded). It starts only inside the window (days of the week or of the month, a start time and length in a named time zone), only while the cluster is available with no rollout running, and not beyond the Kubernetes versions an installed Rancher runs on. Cluster API then rolls the nodes as for any upgrade; a rollout that has started finishes even if the window closes. The last automatic upgrade is recorded on the Cluster as `kubehenge.dev/auto-upgraded`.

## Networking

- **Node addresses** come from IP pools managed in the management cluster; no DHCP is needed on the Proxmox VE bridge.
- **The control plane** of each cluster gets a virtual IP that moves between control-plane nodes.
- **Services of type `LoadBalancer`** get addresses from the cluster's `loadBalancer` range, if it has one: MetalLB in layer 2 mode, without its BGP backend, its address pool applied by Kubehenge's controller in the cluster since its chart has no place for one (and again whenever MetalLB returns, since its CRDs take the pool with them when it goes), or kube-vip as a DaemonSet that answers only for Services, one lease per Service so that their addresses spread over the nodes, with kube-vip's cloud provider handing them out. MetalLB's speakers answer from the control planes too, which kubeadm labels as excluded from load balancers, so that a cluster without workers still has nodes to answer from. On k3s the class switches servicelb off, and the controller deletes the DaemonSets servicelb left, which k3s itself cleans up only while its own cloud controller runs. Every k3s node allows the two forwarding settings servicelb's pods need, which k3s allows only where servicelb is on, so that servicelb's pods run on the old servers too while the control planes roll to switch it back on. Cilium's own L2 announcements are not used: they need Cilium in place of kube-proxy. Kubehenge's admission webhook and BeforeClusterCreate hook refuse addresses outside the nodes' network, on the gateway, the network's own or broadcast address, the API address or the node addresses, or on another cluster's on the same bridge and VLAN. kube-vip's cloud provider never takes back an address it has recorded on a Service, and MetalLB keeps one as requested, so the controller frees a Service of an address outside the range, which no longer holds it against other clusters, and the load balancer gives it a new one.
- **Pod networking** comes from each distribution's own CNI unless another is chosen for the cluster: canal for RKE2, flannel for k3s and Talos. RKE2 also ships Calico and Cilium and installs either itself. kubeadm has none of its own, so one is chosen when a kubeadm cluster is created, Cilium or Calico, and Kubehenge's controller installs it; it does the same for a k3s cluster given Cilium or Calico, whose flannel and network policy controller are then switched off, and for a Talos cluster given either, whose flannel the class then leaves out. On Talos, Cilium leaves the cgroup hierarchy to Talos and runs without `SYS_MODULE`, and Calico installs no FlexVolume driver into Talos's read-only `/usr`. Kubehenge's Cilium chains the portmap plugin, as RKE2's does, so that host ports, the ingress controller's among them, work without Cilium in place of kube-proxy; on k3s the plugin is k3s's own. Calico comes as the Tigera operator's chart, the operator creating Calico's CRDs, and its Installation through the cluster's ClusterResourceSet once they exist: Calico's CRD chart is too large for a Helm release. The CNI is chosen at creation and stays.
- **Pod and service ranges** must stay clear of the nodes' network. Kubehenge refuses to create a cluster whose ranges, its own or its distribution's defaults (Kubernetes' 10.96.0.0/12 for kubeadm's services), overlap it. The interface sets them on every cluster it creates: those asked for, or else the distribution's own when they are clear of the nodes' network, or else the first of a few private ranges that are. Every class honours the Cluster's ranges; the k3s provider reads its own server configuration only, so the k3s class copies them there.
- **The Gateway API** is in every cluster, with no switch: it costs no pod, and gives Traefik's Gateway, Istio's waypoints and anything else that speaks it the same API everywhere. Kubehenge's controller carries one release of upstream's standard-channel install file, built into its binary and checked against its SHA-256 when the binary is built, and applies its CRDs and the admission policy beside them (`safe-upgrades.gateway.networking.k8s.io`) with the cluster's admin kubeconfig once the control plane is up. RKE2 and k3s ship the CRDs in their Traefik CRD charts in some releases; later releases drop them from that chart, which keeps them in the cluster, and ship all of the Gateway API, CRDs and policy, in a chart of its own instead (`rke2-gateway-api-crd`, `gateway-api-crd`), which adopts what it finds. There the controller first waits until the distribution's charts are installed, the Traefik CRD chart and the Gateway API chart where the release has one (its HelmChart is there by then, as the distribution creates all of a release's HelmCharts at once), since Helm refuses to install a chart over objects it does not own and Traefik's chart refuses to install without its CRD chart. Where the distribution has its own Gateway API chart, the Gateway API is the distribution's: the controller applies none of it, at the chart's release whether older than Kubehenge's or not, and mixes none of its own objects in. Otherwise it looks at each object of the bundle in the cluster: one missing gets Kubehenge's; one of Kubehenge's release or newer stays; an older one stays while the latest revision of the Helm release that marks it as its own still holds it, and is taken over and brought to Kubehenge's release once that revision does not. The controller logs each object it applies, and which Helm releases hold the cluster's objects whenever that changes. The policy stays in place too, so that a chart bringing older CRDs, or experimental ones over standard ones, is refused. The distributions' Gateway API charts install only the standard channel, as Kubehenge does; their experimental channel adds only the `gateway.networking.x-k8s.io` CRDs, which neither Traefik's Gateway provider nor Istio's waypoints need. Traefik's Gateway provider is on in every distribution, configured like the rest of Traefik: in the chart values on kubeadm, and on RKE2 and k3s in the `HelmChartConfig` the classes write onto the control planes before the distribution starts, so that its Traefik never runs on the distribution's own values. The certificates add-on's default certificate and HTTPS listener are part of it, rendered from the cluster's `certificates` variable, so switching the default certificate on or off replaces an RKE2 or k3s cluster's control planes one by one. Its chart creates a Gateway, which an API server without the CRDs refuses, so on kubeadm the controller holds Traefik's chart back until the Cluster carries the annotation `kubehenge.dev/gateway-api`, which records the oldest release among the CRDs once they are all there, or once the distribution's Gateway API chart is installed; RKE2's and k3s's helm controller retries until they are. The controller looks at every cluster again each minute, so a distribution upgrade that drops the CRDs is followed within a minute.
